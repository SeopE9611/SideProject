# 샬롬의 집 디자인 시스템

## 1. 문서 목적

이 문서는 샬롬의 집 공개 UI가 일관된 의미 기반 디자인 토큰을 사용하도록 하는 장기 기준이다. 공식 CI가 확정되기 전에도 컴포넌트 구조를 유지하면서 토큰값만 안전하게 교체할 수 있도록 색상, 타이포그래피, 간격, 모션과 접근성 원칙을 정의한다.

페이지별 시각 방향, 레퍼런스 사용 원칙과 디자인 고도화 순서는
[`visual-direction.md`](./visual-direction.md)를 기준으로 한다.

## 2. 현재 상태

- 공식 CI와 공식 브랜드 색상은 아직 확인되지 않았다.
- 현재 팔레트는 따뜻한 세이지를 기반으로 한 임시 토큰이다.
- 공식 자료 확인 시 의미 토큰 이름은 유지하고 값만 교체한다.
- 현재 다크 모드는 지원하지 않는다.
- 현재 공개 페이지는 정보구조와 접근성 기반을 검증하기 위한 1차 UI다.
- 현재 구현을 최종 시각 디자인으로 간주하지 않는다.
- 레퍼런스 기반 전역 디자인 고도화가 남아 있다.
- 실제 승인 콘텐츠와 이미지 연결 전에도 페이지별 구조 차별화를 진행할 수 있다.

## 3. 디자인 원칙

- 평온함
- 신뢰
- 환대
- 따뜻한 일상
- 쉬운 정보 탐색
- 접근성 우선
- 따뜻한 일상, 명확한 안내
- 페이지 목적에 따른 시각적 차별화
- 카드보다 정보 구조 우선
- 감정적 압박 없는 참여 안내

## 4. 색상 토큰

| 토큰 | 값 | 역할 |
| --- | --- | --- |
| `background` | `#F8F5EF` | 페이지 배경 |
| `surface` | `#FFFFFF` | 독립 표면 |
| `surface-subtle` | `#F1F5F2` | 보조 영역 |
| `foreground` | `#24323A` | 기본 글자 |
| `muted-foreground` | `#5F6B66` | 보조 글자 |
| `border` | `#D8DED9` | 장식적 경계 |
| `border-strong` | `#74827B` | 기능적 경계 |
| `primary` | `#355C4A` | 주요 행동과 강조 |
| `primary-hover` | `#2E4F40` | primary 상호작용 |
| `primary-soft` | `#EAF1EC` | 약한 primary 배경 |
| `accent` | `#A85C3A` | 제한적 따뜻한 강조 |
| `focus-ring` | `#A85C3A` | 키보드 포커스 |
| `success` | `#2F6B4F` | 성공 상태 |
| `warning` | `#7A520F` | 경고 상태 |
| `danger` | `#A23B3B` | 오류 상태 |

`border`는 장식적인 구분선에만 사용한다. 입력창, 선택 상태, 기능 식별 경계에는 `border-strong`을 사용한다. 상태별 연한 배경에는 각 `*-soft` 토큰을 사용한다.

## 5. 타이포그래피

외부 웹폰트나 폰트 패키지 없이 Tailwind CSS의 기본 시스템 sans-serif 스택을 사용한다.

| 유틸리티 | 크기 | 행간 | 용도 |
| --- | --- | --- | --- |
| `text-display` | `2.25rem` | `1.2` | 홈의 주요 제목 |
| `text-display-lg` | `3rem` | `1.15` | 넓은 화면의 주요 제목 |
| `text-title` | `2rem` | `1.25` | 페이지 제목 |
| `text-heading` | `1.5rem` | `1.35` | 콘텐츠 제목 |
| `text-body` | `1rem` | `1.75` | 본문 |
| `text-small` | `0.875rem` | `1.6` | 보조 정보 |

## 6. 컨테이너와 간격

- `max-w-site`: `72rem`의 사이트 공통 컨테이너
- `max-w-content`: `48rem`의 읽기 콘텐츠 컨테이너
- `px-page`: `1.5rem`의 기본 좌우 여백
- `px-page-wide`: `2rem`의 넓은 화면 좌우 여백
- `py-section`: `4rem`의 기본 섹션 상하 여백
- `py-section-wide`: `5rem`의 넓은 화면 섹션 상하 여백

## 7. 모서리와 그림자

- `rounded-control`: `0.625rem`으로 컨트롤과 작은 상호작용 표면에 사용한다.
- `rounded-card`: `1rem`으로 향후 카드와 독립 표면에 사용한다.
- `shadow-card`: 전경색을 바탕으로 한 낮은 불투명도의 2단 그림자로 표면의 깊이를 표현한다.
- 모든 콘텐츠 영역을 카드로 만들지 않는다.
- 그림자는 독립 표면과 핵심 안내에 제한한다.
- 문서형 정보와 목록은 구분선·간격·배경을 우선 검토한다.
- 같은 화면에서 카드 스타일을 과도하게 반복하지 않는다.

## 8. 모션

- 빠른 색상 전환은 `--motion-duration-fast`(`150ms`)를 사용한다.
- 표준 전환은 `--motion-duration-standard`(`200ms`)를 사용한다.
- 전환 easing은 `ease-standard`를 사용한다.
- `prefers-reduced-motion: reduce` 환경에서는 스크롤 동작을 즉시 적용하고 애니메이션과 전환 시간을 최소화한다.
- 현재 단계에서는 실제 애니메이션을 추가하지 않는다.
- 자동 슬라이드·자동 재생·장식 목적 패럴랙스를 사용하지 않는다.
- 콘텐츠 등장 애니메이션을 전역 기본 패턴으로 만들지 않는다.
- hover는 클릭 가능한 요소에만 적용한다.
- 모션 제거 후에도 정보와 기능이 유지돼야 한다.

## 9. 접근성 기준

- 상세 접근성 기준과 감사 절차는 `docs/accessibility.md`를 단일 기준 문서로 사용한다.
- 디자인 시스템은 토큰·레이아웃·컴포넌트 수준 규칙을 담당하고, 접근성 문서는 사용자 요구·검증·감사·이슈 관리 기준을 담당한다.
- 접근성 적합 여부는 자동 검사만으로 결정하지 않으며 실제 렌더링, 키보드, 확대와 스크린리더 수동 검증이 필요하다.
- WCAG 2.2 AA를 설계 목표로 하되 전문 검증 전 적합 또는 인증을 마친 것으로 표현하지 않는다.

| 조합 | 대비 |
| --- | ---: |
| `foreground / background` | `12.12:1` |
| `muted-foreground / background` | `5.10:1` |
| `primary / background` | `6.94:1` |
| `primary-foreground / primary` | `7.55:1` |
| `accent / background` | `4.53:1` |
| `border-strong / background` | `3.70:1` |
| `success / success-soft` | `5.60:1` |
| `warning / warning-soft` | `6.31:1` |
| `danger / danger-soft` | `5.68:1` |

- 일반 텍스트 목표는 최소 `4.5:1`이다.
- 큰 텍스트 목표는 최소 `3:1`이다.
- 기능을 식별하는 UI 경계와 아이콘 목표는 최소 `3:1`이다.
- `border`는 장식용이므로 입력창 등 기능적 경계에 사용하지 않는다.
- 포커스 링에는 outline offset을 적용하여 배경 또는 surface와 구분한다.
- 색상만으로 성공, 경고, 오류를 전달하지 않는다.
- 최종 UI 완성 후 실제 렌더링을 다시 검사해야 한다.

## 10. 구현 규칙

- TSX에서 HEX, RGB, OKLCH 값을 직접 사용하지 않는다.
- `text-gray-*`, `bg-white` 같은 원시 색상 대신 의미 토큰을 사용한다.
- 새 색상은 역할과 대비를 검토한 후 `globals.css`에 추가한다.
- 같은 역할에 서로 다른 색상값을 직접 작성하지 않는다.
- 공식 CI 확인 시 컴포넌트가 아니라 토큰값을 수정한다.
- 상태색에는 텍스트, 아이콘, 레이블 등 비색상 단서를 병행한다.
- 접근성 검증 전 공식 적합 인증 표현을 사용하지 않는다.

## 11. 공통 레이아웃 패턴

- 페이지마다 동일한 2열 히어로·카드 그리드를 의무적으로 반복하지 않는다.
- 페이지 목적과 실제 콘텐츠 유형에 따라 편집형·목록형·문서형 구조를 선택한다.
- 관련 링크는 필요한 소수 경로만 제공한다.
- `/support` 강조는 참여 맥락이 있는 영역에 제한한다.
- 카드, CTA, 배경색은 정보의 우선순위를 전달하기 위해 사용한다.

### 헤더

- 공식 로고와 CI가 확인되기 전까지 사이트명과 “공식 홈페이지” 보조 문구로 구성한 텍스트 브랜드를 사용한다.
- 공식 CI가 확정되기 전까지 텍스트 브랜드 왼쪽에 제한적인 `accent` 경계만 사용한다.
- `lg` 이상에서는 가로형 데스크톱 내비게이션을, `lg` 미만에서는 모바일 disclosure 메뉴를 제공한다.
- 헤더는 현재 sticky 또는 fixed 영역이 아니며 문서 흐름에 배치한다.
- 전역 내비게이션의 모든 주요 메뉴는 같은 탐색 계층으로 표시한다.
- `/support`의 강한 CTA 강조는 실제 참여 맥락이 있는 페이지 영역에 제한한다.

### 현재 경로

- Client Component 경계 안에서 `usePathname`으로 현재 경로를 판정한다.
- 현재 경로가 메뉴 경로와 같거나 해당 경로로 시작하면 하위 경로에서도 상위 메뉴를 활성 처리한다.
- 활성 링크에는 `aria-current="page"`를 사용한다.
- 데스크톱의 현재 위치는 하단 경계와 굵은 글자로 표현하며 색상에만 의존하지 않는다.

### 모바일 메뉴

- 실제 `button` 요소에 `aria-expanded`와 `aria-controls`를 적용한다.
- 메뉴 버튼은 아이콘과 보이는 `메뉴`·`닫기` 문구를 함께 제공한다.
- 모바일 항목은 카드형 CTA가 아닌 목록형 구조를 사용하고 현재 경로를 왼쪽 경계, 배경과 굵은 글자로 구분한다.
- 작은 화면 높이에서는 마지막 항목까지 접근할 수 있도록 메뉴 내부 세로 스크롤을 허용한다.
- `/support`를 전역 모바일 메뉴에서 별도의 filled CTA로 표시하지 않는다.
- 메뉴는 Escape, 외부 포인터 클릭, 메뉴 링크 클릭, 경로 변경 시 닫힌다. Escape로 닫으면 메뉴 버튼으로 포커스를 반환한다.
- 문서 흐름과 키보드 순서를 유지하는 disclosure 내비게이션이며 모달이나 전체 화면 드로어가 아니다.
- 포커스 트랩, 배경 오버레이, body 스크롤 잠금은 사용하지 않는다.

### 푸터

- 시설 소개, 바로가기, 연락처의 세 영역으로 구성한다.
- 시설명, 설명, 주소, 전화번호, 주요 메뉴 등 확인된 `siteConfig` 정보만 사용한다.
- 미확정 이메일, 운영시간, 법인정보는 표시하지 않는다.
- 모바일에서는 한 열로 표시하고 화면 폭에 따라 데스크톱 다열 구조로 전환한다.
- `primary` 배경으로 페이지의 종결점을 명확히 표현하며 카드와 그림자는 사용하지 않는다.
- 데스크톱에서는 경계와 여백으로 세 영역을 구분한다.
- 링크에는 밑줄과 명확한 hover·focus 상태를 제공한다.
- `primary` 배경의 링크에는 충분히 대비되는 `primary-foreground` 포커스 outline을 사용한다.

### 메인 페이지

- 메인 페이지는 사이트 전체의 안내 허브로서 소개 중심 히어로, 기본 연락 안내 띠, 세 정보 흐름으로 구성한다.
- 히어로는 사이트 목적과 `/about`, `/life` 우선 경로를 제공한다.
- 강한 filled CTA는 `/about` 하나만 사용하고 `/life`는 낮은 위계의 밑줄 있는 보조 링크로 제공한다.
- 기본 연락처는 히어로 카드가 아닌 별도 연락 안내 띠에 배치하고 `siteConfig.address`, `siteConfig.phone`을 사용한다.
- 다섯 메뉴는 `시설과 생활`, `소식과 참여`, `운영 정보`의 세 정보 흐름으로 구분하며 기존 다섯 라우트를 모두 유지한다.
- 메뉴를 동일한 다섯 카드로 반복하지 않고 각 그룹의 제목·설명·경계·링크 목록을 우선한다.
- `/support`는 홈페이지 정보 탐색 영역에서 별도 filled 카드로 강조하지 않는다.
- 공식 사진이 확보되기 전에는 이미지 프레임이나 가짜 사진을 만들지 않는다.
- 실제 시설 소개·활동·후원 방식은 승인된 콘텐츠가 확보된 후 추가한다.
- 메인 페이지는 Server Component로 유지한다.
- 현재 구조는 홈 전용이며 아직 범용 컴포넌트로 추출하지 않는다.

### 시설 소개 페이지

- 시설 소개는 확인된 기본 정보를 읽는 편집형·문서형 페이지이며, 소개 헤더는 단일 읽기 열로 구성한다.
- 시설명·주소·대표 전화는 `siteConfig`를 사용해 별도 기본 정보 영역에 표시하고, 연락 정보는 `address`와 설명 목록으로 구성한다.
- 공식 연혁·운영 방향·시설 환경은 담당자 확인과 공개 범위 검토 후 추가한다.
- 상세 소개 공개 원칙은 카드가 아닌 편집형 문단 구조로 제공한다.
- 사진과 관계자 정보는 공개 동의와 개인정보 검수를 거친 자료만 사용하며, 승인된 사진이 없으면 텍스트 기반 구조를 유지한다.
- 관련 경로는 `/life`, `/transparency` 두 개로 제한하고 카드가 아닌 링크 목록으로 제공한다.
- `/support`는 이 페이지에서 별도로 강조하지 않는다.
- 페이지는 Server Component로 유지한다.
- 현재 구조는 페이지 전용이며 범용 컴포넌트로 추출하지 않는다.

### 함께하는 생활 페이지

- 함께하는 생활은 안내 예정 범위와 콘텐츠 공개 원칙을 설명하는 단계형 정보 페이지이며, 소개 헤더는 단일 읽기 열로 구성한다.
- 안내 예정 범위는 생활 안내·주요 프로그램·활동 이야기·시설 이용 관련 안내 네 항목을 `01`~`04` 순서형 목록으로 제공한다.
- 네 항목은 현재 서비스 목록이 아니라 공개 범위를 검토하고 있는 정보다.
- 콘텐츠 공개 원칙은 개별 카드가 아닌 경계와 문단으로 구분한다.
- 실제 프로그램 명칭과 운영 내용은 담당자 확인 후 추가한다.
- 생활과 활동 정보는 사실관계와 공개 권한을 확인한 뒤 게시하며, 거주인의 존엄과 사생활 보호를 우선한다.
- 사진·영상·음성은 동의와 개인정보 검수 후 사용한다.
- 관련 경로는 `/news`, `/support` 두 개로 제한하고 같은 탐색 계층으로 제공한다.
- `/support`는 filled CTA로 표시하지 않는다.
- 페이지는 Server Component로 유지한다.
- 현재 구조는 페이지 전용이며 범용 컴포넌트로 추출하지 않는다.

### 샬롬 소식 페이지

- 샬롬 소식은 공지사항과 활동 소식을 찾는 목록 중심 페이지다.
- 상단 소개는 고정 높이 없이 페이지 역할과 현재 게시 상태만 전달하는 간결한 단일 읽기 열로 구성한다.
- 소식 분류는 `공지사항`, `활동 소식` 두 개이며, 검색·필터·탭이 아니라 공개 범위를 안내한다.
- 분류는 카드나 버튼이 아닌 설명 목록과 경계로 구분한 정보 구획으로 제공한다.
- 실제 게시물이 없을 때 카드·그림자·오류 아이콘 없이 간결하고 정상적인 빈 상태를 제공한다.
- 빈 상태에는 `/life`, `/support`를 같은 낮은 위계의 밑줄 있는 텍스트 링크로 제공하고 `/support`를 filled CTA로 표시하지 않는다.
- 가짜 게시물·날짜·작성자·썸네일을 만들지 않는다.
- 게시 원칙은 개별 카드가 아닌 문서형 목록으로 제공한다.
- 게시 전 사실관계와 공개 권한, 개인정보·민감정보, 콘텐츠 접근성을 함께 확인한다.
- 페이지는 Server Component로 유지한다.
- 현재 빈 상태와 원칙 구조는 페이지 전용이며 범용 컴포넌트로 추출하지 않는다.

#### 향후 게시물 목록 표시 구조

- 실제 게시물이 생기면 페이지 중심을 목록으로 전환한다.
- 분류, 제목 링크, 게시일을 기본 정보로 제공한다.
- 각 게시물은 의미상 독립된 `article` 후보로 검토한다.
- 요약은 공개가 승인된 내용이 있을 때만 표시한다.
- 수정일은 실제 수정 여부와 운영 정책이 확정된 경우에만 표시한다.
- 제목 링크만 읽어도 목적을 이해할 수 있도록 작성한다.
- 날짜는 구현 시 `time`과 기계 판독 가능한 `datetime`을 사용한다.
- 썸네일은 필수 요소가 아니다.
- 이미지는 공개 동의와 대체 텍스트 검수를 통과한 경우에만 사용한다.
- 게시물 수가 적을 때 검색·필터를 만들지 않는다.
- 상세 URL, 식별자와 DB·CMS 스키마는 추후 콘텐츠 모델을 확정한 뒤 결정한다.
- 이번 작업에서는 게시물 타입, 샘플 데이터와 상세 경로를 생성하지 않는다.

### 후원과 봉사 페이지

- 후원과 봉사 페이지는 공식 참여 방법과 문의 경로를 제공하기 위한 페이지다.
- 상단 소개는 고정 높이와 보조 카드가 없는 단일 읽기 열로 구성한다.
- 후원과 자원봉사를 서로 다른 정보 흐름으로 분리하되 같은 시각 위계를 적용한다.
- 현재 각 흐름은 실제 신청 단계가 아니라 준비 상태와 확인 후 공개할 정보의 범위를 안내한다.
- 후원 흐름은 후원 방법·참여 절차·문의 범위를 공식 담당자 확인 후 제공한다.
- 자원봉사 흐름은 신청 방식·참여 절차·문의 범위를 운영자 협의 후 제공한다.
- 실제 방법이 미확정인 현재는 filled primary CTA를 제공하지 않는다. 공식 참여 방법이 확정되면 해당 흐름 안에서 주요 CTA 하나를 별도 검토한다.
- 대표 전화는 별도 연락 안내 영역에서 `siteConfig.phone`을 시설 대표 번호로만 표시하고, 후원·자원봉사 전용 접수 번호로 표현하지 않는다.
- 대표 전화는 filled 버튼이 아닌 항상 밑줄이 보이는 텍스트 링크로 제공한다.
- 참여 정보 원칙은 개별 카드가 아닌 제목과 설명을 가진 문서형 목록으로 구성한다.
- 관련 경로는 `/news`, `/transparency` 두 개로 제한하고, 카드가 아닌 같은 위계의 링크 목록으로 제공한다. 메뉴명은 `siteConfig.mainNavigation`에서 가져온다.
- 계좌·온라인 결제·신청 폼·개인정보 입력 UI는 만들지 않는다.
- 페이지는 Server Component로 유지하며 현재 구조는 페이지 전용이므로 범용 컴포넌트로 추출하지 않는다.

#### 향후 참여 기능 검토 기준

- 후원·자원봉사 기능은 실제 운영 방식과 담당자가 확정된 후 구현한다.
- 후원과 자원봉사 기능은 서로 다른 운영 흐름으로 설계한다.
- 실제 공식 방법과 담당자가 확정되기 전에는 행동형 CTA를 제공하지 않는다.
- 주요 CTA는 한 흐름 안에서 원칙적으로 하나만 제공한다.
- 시설 대표 전화를 신청 완료 수단으로 가정하지 않는다.
- 계좌 후원과 온라인 결제를 동일한 기능으로 가정하지 않는다.
- 온라인 결제를 구현할 경우 결제 사업자, 환불, 영수증, 개인정보 처리 기준을 별도 검토한다.
- 입력 폼은 수집 목적·항목·보유기간·처리 담당자가 확정된 후 설계하고, 자원봉사 신청 기능을 구현할 경우 목적에 필요한 최소 개인정보만 수집한다.
- 공개 페이지에 신청자 개인정보나 신청서 원문을 노출하지 않는다.
- 미성년자 참여 기준과 동의 절차는 운영자 또는 전문가 확인 후 결정한다.
- 성공·실패·검증 상태는 실제 신청 흐름이 확정된 후 설계한다.
- 현재 문서와 UI 및 이 기준은 실제 신청 기능이나 데이터 모델 구현이 완료됐다는 의미가 아니다.

- 상단 소개는 고정 높이와 보조 카드가 없는 간결한 단일 읽기 열로 구성한다.

- 네 범위는 현재 실제 필터·독립 라우트·자료 목록이 아니라 정보구조 문서의 검토 대상이다.
- 자료 범위는 카드나 버튼이 아닌 설명 목록 또는 정보 구획으로 제공한다.
- 실제 자료가 없을 때 오류가 아닌 정상적인 빈 상태를 제공한다.

- 빈 상태에는 `/support`, `/news`를 같은 위계의 텍스트 링크로 제공하며 `/support`를 filled CTA로 표시하지 않는다.

- 기준 기간과 수정일은 실제 값이 있을 때만 표시하고, 게시일은 실제 구현 시 `time`과 `datetime`을 사용한다.
- 파일 형식과 용량은 실제 첨부파일 값만 표시한다.

- 검색과 연도 필터는 실제 자료 수와 운영 요구를 확인한 뒤 검토한다.
- 담당자 확인과 공개 승인을 마친 최종 자료만 게시한다.
- 개인정보와 공개가 제한된 내부 정보가 제거됐는지 확인한다.
- 법적 공개 의무와 게시 주기는 운영자 또는 전문가 확인 후 결정한다.
- 관련 링크는 페이지의 타입 안전한 지역 데이터와 `siteConfig.mainNavigation`의 메뉴명을 사용한다.
- 페이지는 Server Component로 유지한다.
- 현재 범위·빈 상태·표시 기준은 페이지 전용이며 범용 컴포넌트로 추출하지 않는다.

#### 향후 운영자료 목록 표시 구조

- 각 자료는 의미상 독립된 목록 항목 또는 `article` 후보로 구성한다.
- 자료명 링크를 주된 상호작용으로 삼는다.
- 자료 분류·자료명·기준 기간·게시일·파일 형식·용량을 실제 값으로 제공한다.
- 기준 기간은 실제 값이 있을 때만 표시한다.
- 게시일은 구현 시 `time`과 기계 판독 가능한 `datetime`을 사용한다.
- 수정일은 실제 교체·수정 여부와 운영 정책이 확정된 경우에만 표시한다.
- 파일명과 링크 문구만으로 자료의 목적을 이해할 수 있도록 작성한다.
- 스캔 이미지만 제공하기보다 접근 가능한 웹 텍스트 또는 읽을 수 있는 PDF를 우선 검토한다.
- PDF만 제공하는 경우에도 핵심 내용을 웹페이지에서 설명하는 방안을 검토한다.
- 개인정보와 내부 정보가 제거된 공개용 최종 파일만 연결한다.
- 목록·상세 URL, 식별자와 파일 저장소 구조는 콘텐츠 모델 확정 후 결정한다.
- 이번 단계에서는 자료 타입·샘플 데이터·첨부파일·상세 라우트를 만들지 않는다.

### 404 페이지

- 루트 `src/app/not-found.tsx`에서 찾을 수 없는 경로를 처리한다.
- 루트 레이아웃은 `html`, `body`만 제공하므로 404 내부에서 공개 사이트 셸을 구성한다.
- `SkipLink`, `SiteHeader`, `main#main-content`, `SiteFooter`를 사용한다.
- 짧은 상태 문구, H1, 설명과 홈 복귀 행동으로 구성하며 홈 복귀를 유일한 본문 행동으로 제공한다.
- 홈 링크는 하나의 filled primary 링크로 제공한다.
- 검색·추천·이전 페이지 이동 기능을 만들지 않는다.
- 카드·그림자·아이콘·일러스트·거대한 404 숫자를 사용하지 않는다.
- 404 상태를 alert 또는 live region으로 표현하지 않는다.
- H1 한 개와 명확한 포커스 표시를 유지한다.
- Server Component를 유지하고 404 페이지를 `(public)` 아래로 이동하지 않는다.
- 현재 구조는 404 전용이며 범용 오류 컴포넌트로 추출하지 않는다.
- HTTP 상태 처리와 Next.js 특수 파일 동작을 수동으로 우회하지 않는다.

## 13. 변경 관리 원칙

의미 토큰 이름은 UI 역할을 기준으로 안정적으로 유지한다. 공식 CI나 브랜드 자료가 확인되면 접근성 대비를 다시 계산하고 `globals.css`의 토큰값을 우선 변경하며, 컴포넌트에 개별 색상값을 추가하지 않는다. 토큰의 역할이나 사용 기준이 달라지면 이 문서와 구현을 함께 갱신한다.
