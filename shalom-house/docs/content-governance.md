# 콘텐츠 운영 및 공개 기준

## 공개 인물 및 활동사진 안전 기준

- 공개 직원 소개에는 당사자와 운영 책임자가 승인한 이름·직책·업무와 사진만 사용한다.
- 거주인의 공개 인물 디렉터리를 만들지 않는다.
- 거주인의 이름·나이·생년월일·장애·건강·개별 지원 기록을 프로필로 공개하지 않는다.
- 거주인 관련 공개 정보는 개인을 식별할 수 없는 승인 범위로 제한한다.
- 활동사진은 사진별 공개 동의, 게시 기간과 철회 상태를 확인한 자료만 사용한다.
- fixture에는 사람의 실제 프로필로 오해할 수 있는 인물 프로필을 만들지 않는다.

## 기본 원칙과 상태

거주인의 존엄성과 사생활을 홍보보다 우선한다. 공개 필요성이 명확한 최소 정보만 게시하고 정확성·권한·개인정보와 민감정보·접근성을 확인한 뒤 승인한다. 내부 문서 원본을 공개자료로 사용하지 않으며 오래된 정보는 정기 검토한다.

- **`official`**: 운영 담당자가 확인하여 공개할 수 있는 공식 콘텐츠다.
- **`fixture`**: 레이아웃, 밀도, 반응형과 기능 검증용 테스트 콘텐츠이며 중앙 fixture 모듈에서만 관리한다.
- **`demo`**: 시연이나 자동화를 위한 시나리오 콘텐츠이며 공개 목록에서 기본 제외하고 운영 데이터와 분리한다.

`fixture`와 `demo`는 목적이 다르며 어느 것도 `official`로 자동 전환하거나 운영 공개할 수 없다.

## 공식 콘텐츠 메타데이터

`official` 콘텐츠는 가능한 범위에서 출처, 작성일, 검토일, 공개일, 수정일, 검수자 또는 승인 역할, 공개 범위, 게시 상태, 재검토 예정일, 사진·영상 동의 상태와 관련 첨부파일 승인 상태를 관리한다. 실제 담당자 이름은 이 기준 문서에서 정하지 않으며 자료 수집과 확인 절차는 [`operations/official-content-intake.md`](./operations/official-content-intake.md)가 담당한다.

## 공개 범위

운영자 승인 후 공식 소개, 승인된 주소·연락처, 프로그램·후원·자원봉사 안내, 개인정보가 제거된 활동 소식과 승인된 운영자료를 공개할 수 있다. 얼굴·이름·음성·인터뷰·사례와 개인을 추정할 수 있는 위치·일정은 별도 동의와 검수가 필요하다.

주민등록번호, 장애·진단·의료·복약·상담·개별 지원 기록, 보호자·가족관계·개인 연락처, 비공개 후원자 정보, 내부 인사·사건·회의·행정 자료, 미승인 재무자료·원본 신청서·계정정보는 공개하지 않는다. 정보 조합의 식별 가능성도 확인하며 불분명하면 게시하지 않는다.

## 사진·영상·음성 동의와 철회

- 촬영 동의와 홈페이지 공개 동의를 구분하고 공개 채널과 게시 기간을 확인한다.
- 동의 철회 접수 경로와 처리 책임은 운영자가 확정해야 한다.
- 철회 또는 개인정보 우려가 접수되면 우선 비공개한 뒤 확인한다.
- CDN, 썸네일, 캐시와 검색엔진에 남은 사본 제거 절차를 별도로 검토한다.
- 동의 문서의 법적 형식과 보관 기간은 전문가와 운영자 확인이 필요하다.
- 배경의 문서, 이름표, 주소, 차량번호와 파일 메타데이터를 검수하고 승인된 공개용 파일만 사용한다.

## placeholder와 fixture 안전 규칙

비인물 시설·공간·활동 이미지, 프로젝트 내부 placeholder 및 중앙 fixture 데이터에 등록한 URL 이미지만 허용한다. 실제 거주인으로 오해할 인물·출처 불명 이미지, 실제 시설 사진 같은 설명, 컴포넌트의 임의 URL 하드코딩과 URL 중복은 금지한다.

향후 테스트 데이터는 다음 중앙 모듈에서 관리하되 이번 문서 작업에서는 파일을 만들지 않는다.

```text
src/content/fixtures/
├─ home.fixture.ts
├─ news.fixture.ts
├─ life.fixture.ts
├─ support.fixture.ts
└─ transparency.fixture.ts
```

- fixture는 중앙 모듈 밖에 중복 작성하지 않고 코드 또는 명시적 상태값으로 테스트 데이터임을 식별한다.
- Preview에서도 실제 기관 정보처럼 보이지 않게 하며 운영 배포 전에 fixture 잔존 여부를 검사한다.
- fixture를 official로 바꿀 때 상태만 변경하지 않고 공식 자료로 교체해 재승인한다.
- URL placeholder 서비스 장애의 이미지 실패 상태를 검증하고 외부 URL에 개인정보나 추적 파라미터를 넣지 않는다.

## 파일 업로드와 보안

향후 업로드 기능은 허용 형식, 최대 용량, MIME type·확장자 검증, 파일명 정규화, 악성 파일 검사, 공개·비공개 저장 위치 분리, 임의 실행 파일 차단, 개인정보·메타데이터 검사, 접근 권한, 삭제·복구, 백업과 감사 기록을 적용한다. 구체적 패키지와 CMS·저장소 구현은 이번 문서에서 확정하지 않고 [`technical/content-platform-architecture.md`](./technical/content-platform-architecture.md)가 담당한다.

## 분야별 승인 원칙

- 직원 이름·직책·업무 연락처는 승인 범위만 공개하고 변경 시 갱신한다.
- 계좌, 예금주, 후원 방식과 세액공제 안내는 담당자 또는 전문가 확인 전 게시하지 않는다.
- 자원봉사 신청 정보는 최소화하고 신청서와 연락처를 공개 게시물에 노출하지 않는다.
- 투명성 자료는 승인된 최종본만 사용하며 제목, 기준 기간, 게시일, 수정일, 형식과 크기를 표시한다.

## 긴급 비공개

개인정보·민감정보 노출 가능성, 동의 철회, 잘못된 계좌·연락처·일정, 공개 권한 미확인 문서, 보안 위험 첨부파일 또는 거주인·관계자의 안전 우려가 있으면 승인 절차 완료를 기다리지 않고 우선 비공개할 수 있다. 이후 사실을 확인하고 수정과 재승인 여부를 결정한다.

## 검색엔진과 외부 캐시

- 페이지 비공개만으로 검색결과와 외부 캐시가 즉시 제거되지 않을 수 있다.
- 필요하면 검색엔진 삭제 요청, OG 이미지와 CDN 캐시 제거를 검토한다.
- 외부 SNS 공유 사본은 별도 대응이 필요할 수 있다.
- 실제 처리 책임자와 절차는 운영자 확인이 필요하다.

## 수정·삭제와 감사 기록

단순 수정, 비공개, 삭제, 교체와 보존의 차이는 운영 정책에서 확정한다. 중요 콘텐츠에는 가능한 범위에서 변경 전후, 변경 사유, 변경 역할, 변경일, 승인 여부와 긴급 비공개 여부를 기록한다. 구체적인 CMS 감사 기록 구현은 기술 아키텍처 문서가 담당한다.

## 작성·검수·공개 절차

```text
작성 → 개인정보·민감정보 확인 → 사실과 공개 권한 확인 → 접근성 확인
→ 승인 → 공개 → 정기 검토 → 수정·비공개·삭제
```

CMS 구현 여부와 관계없이 공개 전 검수를 생략하지 않는다. 최종 승인 역할, 동의 양식과 보관 기간, 검수 주기, 파일 정책, 역할·권한 및 긴급 처리 책임은 운영자 확인이 필요하다.

## 프로그램 게시 원칙

실제 운영이 확인된 프로그램만 게시하며 일정·참여 대상·운영 상태는 담당자 확인 후 작성한다. 거주인 개인정보와 개별 지원 내용, 승인되지 않은 사진은 게시하지 않는다. 프로그램을 근거 없이 의료·치료·재활 서비스로 표현하지 않으며 게시 전 검토와 승인을 반드시 거친다.

## 활동사진 1차 보관 정책

활동사진 초안은 홈페이지 공개 동의 상태와 게시 가능 기간을 기록하되 private Supabase Storage에만 보관한다. 보관 처리는 Storage object 영구 삭제가 아니며 공개, 이미지 교체·영구 삭제와 동의 철회 처리는 후속 단계에서 운영 절차와 함께 구현한다. 동의 원본이나 실명은 저장하지 않고 내부 참조 코드만 기록한다.

Supabase 비공개 보관소의 운영 환경 변수는
`SHALOM_SUPABASE_URL`, `SHALOM_SUPABASE_SECRET_KEY`,
`SHALOM_SUPABASE_GALLERY_PRIVATE_BUCKET`이며 비밀 값은 코드와 문서에 기록하지 않는다.

## 활동사진 공개와 동의 철회
승인된 활동사진도 private Storage의 단일 원본으로 유지한다. 공개 페이지에는 동의·승인 상태, 참조 코드, 원본 파일명 및 Storage 위치를 노출하지 않는다. 공개 미디어 API는 매 요청마다 게시·승인·동의·철회·게시 기간을 다시 확인하며 public URL과 signed URL을 사용하지 않고 `Cache-Control: no-store`로 응답한다. 동의 철회는 게시 중인 사진을 즉시 비공개로 전환하며 철회 복구는 현재 지원하지 않는다.

## 자료공개 초안 거버넌스

자료공개 문서는 개인정보 검토 상태(`pending`/`confirmed`)와 최종본 상태(`draft`/`final`)를 명시하고 초안 → 검토 요청 → 승인 또는 반려 → 게시 흐름으로 관리한다. 검토 요청과 게시 전에는 개인정보 검토 완료, 최종본, 미보관·미삭제 조건을 모두 확인한다. PDF는 private bucket의 단일 원본으로 유지하며 public URL과 signed URL을 사용하지 않는다. 모든 관리자 상태 전이는 optimistic locking과 MongoDB transaction 안의 감사 이벤트로 기록한다. 공개 PDF API는 매 요청마다 게시·승인·준비 상태를 재검증하고 `Cache-Control: no-store`로 전달하므로 게시 중단 직후 목록에서 제외되며 PDF 경로도 404가 된다. 공개 화면에는 Storage 위치, 원본 파일명, SHA-256, 감사·검토·승인 내부 정보를 노출하지 않는다.

## 관리자 역할과 서버 권한

- `admin`은 전체 권한을 가진다.
- `editor`는 초안 작성·수정·보관·검토 요청을 담당한다.
- `reviewer`는 승인·반려와 활동사진 동의 철회를 담당한다.
- `publisher`는 게시·게시 중단과 활동사진 동의 철회를 담당한다.
- 모든 쓰기 권한은 API에서 서버 강제한다. UI 숨김은 보조 수단이며 보안 경계가 아니다.
- 기존 `admin` 계정은 영향을 받지 않는다.


## 관리자 소프트 삭제와 복구

뉴스, 프로그램, 활동사진, 자료공개 삭제는 MongoDB 문서의 `deletedAt`을 기록하는 소프트 삭제이며 영구 삭제는 지원하지 않는다. 게시 중 콘텐츠도 삭제 즉시 공개 상태가 해제된다. 활동사진 이미지와 자료공개 PDF의 Supabase Storage object는 삭제하지 않고 복구 시 그대로 재사용한다. 복구는 이전 게시 상태를 되살리지 않고 항상 `draft`·`pending` 상태로 전환하며, 검토·승인·게시 절차를 다시 거쳐야 한다. 삭제와 복구는 시스템 관리자만 수행하며 `expectedUpdatedAt` 기반 optimistic locking을 적용하고 상태 변경과 감사 이벤트를 같은 MongoDB transaction에 기록한다.

## 시스템 관리자 일반 콘텐츠 바로 게시

- 시스템 관리자는 공지사항·활동소식·프로그램 초안을 확인 checkbox로 재확인한 뒤 바로 게시할 수 있다.
- 바로 게시는 승인과 게시를 하나의 MongoDB transaction에서 처리하고 감사 기록을 남기며, UI 노출과 별도로 API가 `content.direct_publish` 권한을 강제한다.
- `editor`·`reviewer`·`publisher`의 검토 요청·승인/반려·게시 역할 분리 절차는 그대로 유지한다.
- 공개 동의가 필요한 활동사진과 개인정보·최종본 확인이 필요한 자료공개 PDF는 바로 게시 대상이 아니다.
- 내부 `news` 도메인과 경로는 유지하고 관리자 표시명만 `소식 관리`를 사용한다.

## 공식 콘텐츠 CMS 1차

시설개요와 원장 인사말은 MongoDB에서 관리하며 시스템 관리자만 수정할 수 있다. 문서가 없으면 기존 코드 기본 콘텐츠를 유지하지만 DB 장애는 기본 콘텐츠로 위장하지 않는다. 저장은 즉시 공개 페이지에 반영되고 optimistic locking을 적용하며 콘텐츠와 감사 이벤트를 같은 transaction에 기록한다. 공개 페이지의 편집 링크는 권한 있는 관리자에게만 보인다. 원장 이름은 명시적으로 공개를 설정한 경우에만 표시한다. 주민·입소자 개별 정보는 CMS 대상이 아니며 직원·생활공간 관리는 후속 단계다.

## 직원 소개 공개 거버넌스

직원 소개는 시스템 관리자만 초안·공개·보관 상태와 표시 순서를 관리한다. 직원 이름은 명시적인 공개 확인과 내부 확인 근거가 모두 있을 때만 공개하며 근거 자체는 외부에 노출하지 않는다. optimistic locking과 동일 transaction의 감사 기록을 적용한다. 사진과 생활공간 CMS는 후속 단계이고 입소자 개별 프로필은 대상이 아니다.
