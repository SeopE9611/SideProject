# 샬롬의 집 웹 접근성 기준 및 감사 지침

## 1. 문서 목적과 적용 범위

이 문서는 장애인과 고령자를 포함한 모든 사용자가 샬롬의 집 홈페이지의 공개 정보와 기능에 접근할 수 있도록 기획·디자인·개발·콘텐츠·QA 전 과정에서 계속 사용하는 기준이다. 현재 공개 홈페이지뿐 아니라 향후 게시물, 이미지, 영상, 문서, 폼과 관리자 작성 콘텐츠에도 적용한다.

접근성은 기술 구현이나 출시 직전 검사에 한정되지 않는다. 쉬운 정보 구조, 명확한 문장과 예측 가능한 동작도 요구사항에 포함한다. 이 문서는 접근성 품질인증이나 법률 자문을 대신하지 않으며, 현재 구현이 WCAG 2.2 AA 전체를 충족한다고 선언하지 않는다. 자동화 검사 결과만으로 접근성 작업의 완료를 판단하지 않는다.

## 2. 적용 기준과 우선순위

### 1순위: WCAG 2.2 Level AA

- W3C가 발행한 국제 웹 접근성 기술 기준인 WCAG 2.2를 규범적 우선 기준으로 삼고 Level AA를 설계 목표로 한다.
- 인식의 용이성, 운용의 용이성, 이해의 용이성, 견고성의 네 원칙을 사용한다.
- 실제 적합성 판단에는 개별 성공 기준에 따른 검증이 필요하다.
- AAA 전체 충족을 프로젝트 목표로 선언하지 않는다.
- AA를 만족하더라도 모든 장애인의 모든 필요를 해결한다고 표현하지 않는다.

### 2순위: 국내 웹 콘텐츠 접근성 지침 2.2

- 국내 환경과 심사 기준을 검토하기 위한 규범적 기준으로 사용한다.
- 실제 법적 의무와 품질인증 범위는 운영자 또는 관련 전문가의 확인 후 확정한다.
- 국제 기준과 국내 기준의 차이가 확인되면 더 엄격하거나 사용자에게 유리한 방향을 우선 검토한다.

### 보조 자료: W3C WAI와 NULI

- W3C WAI Understanding Documents, Techniques, Easy Checks와 웹 접근성 평가 안내는 성공 기준의 사용자 영향과 구현·평가 방법을 이해하기 위한 지원 문서다.
- NULI 웹 접근성 교육·아티클·개발 도구, WAI-ARIA UI Example과 NWAGON은 한국어 실무 참고 및 평가 보조 자료다. NULI 자료를 국가표준이나 법률 자체로 표현하지 않는다.
- 규범적 성공 기준과 지원·교육·도구 자료의 역할을 혼동하지 않는다. 적용 계층은 `WCAG 2.2 성공 기준 → 국내 접근성 지침 → W3C 지원 문서 → NULI 실무 참고 자료`다.
- WCAG 3.0은 아직 작업 초안이므로 향후 동향 참고 자료로만 구분하고 현재 적합성 기준으로 사용하지 않는다.
- 평가 도구 결과만으로 WCAG 적합이나 품질인증을 선언하지 않는다.

## 3. 주요 사용자와 기능적 요구

장애 유형은 개인의 능력이나 웹 이용 방식을 고정적으로 결정하지 않는다. 같은 사용자도 환경, 과업과 보조기술에 따라 서로 다른 요구를 가질 수 있으므로 다음 요구를 함께 검토한다.

### 시각장애 및 저시력

- 스크린리더로 제목·랜드마크·링크 목적을 이해할 수 있어야 한다.
- 정보 이미지에는 목적에 맞는 대체 텍스트가 필요하다.
- 텍스트 확대와 화면 확대 시 정보와 기능이 손실되지 않아야 한다.
- 포커스 위치와 현재 위치를 시각적으로 확인할 수 있어야 한다.
- 텍스트와 UI에 충분한 대비가 필요하다.

### 색각 특성

- 색상만으로 현재 상태·성공·오류·선택 상태를 전달하지 않는다.
- 텍스트, 굵기, 모양, 레이블 등 비색상 단서를 병행한다.

### 청각장애 및 난청

- 영상에는 자막 또는 동등한 대체 수단을 검토한다.
- 음성만으로 필수 정보를 전달하지 않는다.
- 자동 재생 음성을 사용하지 않는다.

### 지체·운동장애

- 모든 기능을 키보드만으로 조작할 수 있어야 한다.
- 드래그만으로 수행해야 하는 기능을 만들지 않는다.
- 포인터 취소와 충분한 대상 크기를 고려한다.
- 시간 제한이 필요한 기능은 연장·해제 방안을 검토한다.

### 인지·학습·언어 관련 요구

- 쉬운 한국어를 사용하고 한 문장에 과도한 내용을 넣지 않는다.
- 메뉴와 기능의 위치·이름을 일관되게 유지한다.
- 다음 동작을 예측할 수 있는 링크와 버튼 문구를 사용한다.
- 오류 발생 시 원인과 해결 방법을 함께 안내한다.
- 기억에 의존하는 반복 입력을 최소화한다.

### 고령 사용자

- 충분한 글자 크기와 행간을 사용하고 작은 클릭 영역을 지양한다.
- 명확하고 일관된 내비게이션을 제공한다.
- 과도한 움직임과 짧은 시간 제한을 지양한다.
- 전문용어·행정용어는 가능한 한 쉬운 표현으로 설명한다.

## 4. 프로젝트 접근성 원칙

### 인식의 용이성

- 텍스트 아닌 콘텐츠에 대체 수단을 제공하고 색상에만 의존하지 않는다.
- 충분한 대비를 유지하고 확대·reflow·텍스트 간격 변경에 대응한다.
- 의미 구조와 시각적 구조를 일치시킨다.

### 운용의 용이성

- 키보드로 완전히 조작할 수 있게 하고 명확하며 가려지지 않는 포커스를 제공한다.
- 본문 바로가기와 충분한 터치·포인터 대상을 제공한다.
- 과도한 시간 제한과 움직임을 지양하고 현재 위치와 탐색 경로를 제공한다.

### 이해의 용이성

- 문서 언어를 지정하고 메뉴와 기능을 예측 가능하게 유지한다.
- 링크·버튼 목적을 명확히 표현하고 쉬운 한국어를 사용한다.
- 입력 오류의 원인과 해결 방법을 제공하고 반복 입력을 최소화한다.

### 견고성

- 기본 HTML 의미 요소를 우선하며 ARIA는 기본 HTML로 표현할 수 없는 경우에만 보완적으로 사용한다.
- 접근 가능한 이름·역할·상태를 제공한다.
- 브라우저와 보조기술 조합에서 수동 검증한다.
- 잘못된 ARIA보다 올바른 기본 HTML을 우선한다.

## 5. 구현 기준

### 문서와 랜드마크

- 문서 기본 언어는 `ko`이며 페이지 본문에는 하나의 `main` 랜드마크를 사용한다.
- 공통 `header`, `nav`, `main`, `footer` 구조를 유지한다.
- 같은 페이지에서 중복되거나 모호한 `nav`에는 구분 가능한 레이블을 제공한다.
- 본문 바로가기 링크를 제공한다.
- 각 페이지의 `h1`은 원칙적으로 한 개이며 시각적 크기 때문에 제목 단계를 건너뛰지 않는다.

### 링크와 버튼

- 이동은 링크, 동작은 버튼을 사용한다.
- 링크 텍스트만 읽어도 목적을 예측할 수 있게 하며 `여기`, `더보기`, `클릭`만으로 목적을 전달하지 않는다.
- 새 창을 열 경우 사전에 알린다.
- 카드 전체 링크 내부에는 별도의 중첩 상호작용 요소를 두지 않는다.
- 시각적 레이블과 접근 가능한 이름이 불일치하지 않게 한다.

### 키보드와 포커스

- 모든 기능은 `Tab`, `Shift+Tab`, `Enter`, `Space`, 방향키 등 해당 위젯에 적절한 키로 조작할 수 있어야 한다.
- 포커스 순서는 시각적 순서와 논리적으로 일치해야 하며 포커스 표시를 제거하지 않는다.
- 포커스가 고정 헤더·메뉴·오버레이에 가려지지 않아야 한다.
- 메뉴를 `Escape`로 닫을 때 적절한 위치로 포커스를 돌려보낸다.
- 페이지 이동 후 포커스와 화면 읽기 흐름은 실제 브라우저와 스크린리더에서 검증한다.

### 대상 크기

- 주요 링크와 버튼은 가능한 한 최소 `44 × 44 CSS px` 수준의 터치 영역을 목표로 한다.
- WCAG 최소 성공 기준 충족 여부와 별개로 고령자와 운동장애 사용성을 고려해 여유 있는 영역을 사용한다.
- 인접 대상 사이에 오작동을 줄일 수 있는 간격을 제공한다.

### 색상과 대비

현재 디자인 토큰 조합의 계산값은 다음과 같다.

```text
foreground / background: 12.12:1
muted-foreground / background: 5.10:1
primary / background: 6.94:1
primary-foreground / primary: 7.55:1
accent / background: 4.53:1
border-strong / background: 3.70:1
```

- 이 수치는 토큰 색상 조합 계산값이며 실제 전체 UI 적합성을 증명하지 않는다.
- 실제 글자 크기, 굵기, 투명도, 배경 중첩과 `hover`·`focus`·`disabled` 상태를 별도로 검사한다.
- 장식용 `border`는 기능적 경계 대비의 근거로 사용하지 않고 기능 경계에는 `border-strong` 등 충분한 대비의 토큰을 사용한다.

### 확대와 reflow

- 브라우저 200% 확대에서 정보와 기능 손실이 없어야 한다.
- 400% 확대 또는 약 320 CSS px 폭에서 가로 스크롤 없이 핵심 콘텐츠를 사용할 수 있어야 한다.
- 의미 있는 표·코드·지도처럼 본질적으로 2차원인 콘텐츠는 별도로 검토한다.
- 텍스트가 잘리거나 겹치지 않아야 하며 고정 높이로 본문을 제한하지 않는다.

### 텍스트 간격

다음 사용자 text spacing 스타일을 적용해도 콘텐츠 손실이 없어야 한다.

```text
line-height: 1.5
paragraph spacing: 2em
letter spacing: 0.12em
word spacing: 0.16em
```

실제 검증 결과가 없으면 충족한 것으로 기록하지 않는다.

### 움직임

- `prefers-reduced-motion`을 존중한다.
- 자동 슬라이드와 자동 재생을 지양하고 깜빡임과 과도한 패럴랙스를 사용하지 않는다.
- 애니메이션은 정보 이해나 상태 변화에 필요한 경우에만 사용하며 움직임을 제거해도 정보와 기능이 유지돼야 한다.

### 이미지와 미디어

- 정보 이미지에는 목적에 맞는 대체 텍스트를 제공하고 장식 이미지는 보조기술에서 제외한다.
- 대체 텍스트에 불필요하게 외모와 장애를 묘사하지 않는다.
- 영상의 자막, 대본과 화면해설 필요성을 검토한다.
- 이미지에 포함된 글자를 주요 정보 전달 수단으로 사용하지 않는다.

### 폼과 오류

현재 공개 폼은 없지만 향후 다음 기준을 적용한다.

- 모든 입력에 연결된 레이블을 제공하고 필수 입력을 색상이나 별표만으로 설명하지 않는다.
- 오류 위치·원인·해결 방법을 안내하고 오류 발생 후 적절한 포커스 이동 또는 요약을 제공한다.
- 입력 목적에 맞는 `autocomplete`를 검토한다.
- 같은 과정에서 이미 입력한 정보를 불필요하게 반복 요구하지 않는다.
- 인증 과정은 퍼즐·기억·전사 같은 인지 기능 테스트에만 의존하지 않는다.

### 문서와 PDF

- 핵심 정보는 가능한 한 웹페이지에도 제공하고 스캔 이미지만으로 된 PDF를 지양한다.
- 문서 제목, 기준 기간, 게시일, 파일 형식과 용량을 안내한다.
- PDF 자체의 제목·태그·읽기 순서·표·대체 텍스트를 검증한다.
- 공개 승인된 최종 파일만 연결하며 파일 접근성은 웹페이지 접근성과 별도로 검사한다.

향후 이미지·영상·폼·PDF는 아직 실제 콘텐츠가 없으므로 이 문서의 기준을 적용한 뒤 별도로 검증하며 상태를 `향후 콘텐츠 적용`으로 관리한다. 브라우저 동작과 보조기술 결과는 이 정적 감사만으로 확인하지 않고 `수동 검증 필요`로 관리한다.

## 7. 현재 정적 감사만으로 확인할 수 없는 항목

- 실제 브라우저 렌더링의 대비
- 200%·400% 확대와 320 CSS px reflow
- 사용자 text spacing
- 키보드 전체 탐색 순서와 포커스 가림 여부
- Windows forced-colors
- 스크린리더의 제목·랜드마크·링크 읽기
- 클라이언트 경로 이동 후 포커스와 안내
- 모바일 화면 회전
- 터치 오작동과 실제 대상 크기
- 브라우저별 동작 차이
- 향후 이미지 대체 텍스트
- 향후 영상 자막·대본·화면해설
- 향후 폼의 레이블·오류·자동완성
- 향후 PDF와 첨부파일 접근성
- 실제 장애인 및 고령 사용자 평가

자동 도구에서 오류가 나오지 않더라도 위 항목이 자동으로 충족되는 것은 아니다.

## 8. 수동 검증 매트릭스

| 구분 | 검증 범위 |
| --- | --- |
| 대상 경로 | `/`, `/about`, `/life`, `/news`, `/support`, `/transparency`, 존재하지 않는 경로 |
| 화면 너비 | 320px, 360px, 390px, 768px, 1024px, 1440px |
| 확대 | 100%, 200%, 400% |
| 입력 방식 | 키보드, 마우스, 터치 |
| 가능한 보조기술 환경 | NVDA + Chrome 또는 Firefox, VoiceOver + Safari, TalkBack + Chrome, Windows forced-colors, `prefers-reduced-motion` |

- 실행한 환경만 결과를 기록하고 실행하지 않은 환경을 충족한 것으로 표시하지 않는다.
- 브라우저·운영체제·보조기술 버전을 함께 기록한다.
- 자동 검사와 수동 검사를 구분한다.
- 장애인 또는 고령 사용자 평가가 없다면 사용자 평가 완료로 표시하지 않는다.

### 문서 구조

- 페이지 title과 문서 언어
- `header`, `nav`, `main`, `footer`
- `h1`부터 `h3`까지 제목 순서와 제목만 탐색했을 때의 구조 이해
- 중복되거나 비어 있는 제목 유무

### 키보드

- 본문 바로가기와 모든 링크·버튼 접근
- 논리적 Tab 순서, 포커스 표시와 가림 여부
- 모바일 메뉴 열기·닫기, `Escape`, `Shift+Tab`
- 키보드 함정 유무

### 확대와 reflow

- 200%와 400% 확대, 가로 스크롤 여부
- 텍스트 잘림, 카드 겹침과 고정 높이 문제
- 모바일 메뉴 사용 가능 여부

### 색상과 시각 표시

- 일반·큰 텍스트, UI 경계와 포커스 대비
- 색상 외 현재 상태 단서
- forced-colors에서 정보 유지

### 링크와 이름

- 링크 목적과 중복 링크 이름의 맥락
- 시각적 문구와 접근 가능한 이름
- 전화 링크, 카드 전체 링크와 새 창 여부 안내

### 움직임

- reduced motion 적용, 자동 재생과 깜빡임 유무
- 움직임 없이 정보 유지

### 읽기와 이해

- 쉬운 한국어, 과도하게 긴 문장과 전문용어 설명
- 상태와 후속 행동의 명확성
- 페이지별 내비게이션과 표현의 일관성

## 9. 접근성 이슈 기록 형식

모든 후속 이슈는 다음 필드를 사용한다.

```text
ID
발견일
상태
심각도
대상 경로
대상 파일 또는 컴포넌트
관련 기준
검사 환경
재현 절차
현재 결과
예상 결과
사용자 영향
수정 방향
검증 결과
```

### 차단

- 핵심 정보 또는 기능에 접근할 수 없음
- 키보드 함정
- 스크린리더로 핵심 기능 사용 불가
- 심각한 개인정보 또는 안전 관련 문제

### 높음

- 주요 경로나 기능 사용이 상당히 어려움
- 포커스 유실
- 제목·레이블·이름 오류로 목적 파악이 어려움
- 확대 시 핵심 정보 손실

### 보통

- 우회는 가능하지만 반복적인 불편이나 혼란 발생
- 링크 문구, 구조, 대비, 대상 크기 등의 문제

### 낮음

- 핵심 사용을 차단하지 않지만 일관성 또는 편의 개선 필요
- 권고 수준의 개선

심각도는 개발 난이도가 아니라 사용자 영향으로 판단한다.

## 10. 후속 접근성 작업 순서

1. 기준 문서와 정적 감사 확정
2. Vercel Preview 전역 키보드·확대·reflow 감사
3. 공통 레이아웃과 내비게이션 문제 수정
4. 페이지별 제목·링크·포커스·대비 수정
5. 스크린리더 검증
6. 자동 접근성 검사 도구 보조 적용
7. 실제 콘텐츠·이미지·문서 추가 시 접근성 검수
8. 장애인 및 고령 사용자 평가 검토
9. 최종 전문 접근성 심사 또는 품질인증 필요성 검토

자동 검사 도구 설치를 첫 단계로 삼지 않으며 공통 문제를 먼저 해결한 뒤 페이지별 문제를 해결한다.

## 11. 완료 판단 원칙

- 접근성은 한 번의 완료 작업이 아니라 지속 관리 항목이다.
- 신규 페이지·컴포넌트·콘텐츠·파일 추가 시 같은 기준을 다시 검토한다.
- `typecheck`, `lint`, `build` 성공은 접근성 적합성 검증이 아니다.
- axe, Lighthouse, NWAGON 등의 자동 검사 결과는 보조 자료다.
- 수동 검사와 보조기술 검사가 필요하다.
- 전문 심사 전 접근성 인증 또는 WCAG 전체 적합을 의미하는 표현을 사용하지 않는다.
- 알려진 접근성 문제가 남아 있다면 문서에 상태와 후속 계획을 기록한다.
