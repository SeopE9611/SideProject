# 샬롬의 집 공식 홈페이지 요구사항

## 제품 정의

샬롬의 집 홈페이지는 장애인거주시설의 공식 시설 정보와 생활 기록을 제공하는 기관 홈페이지다. 감성 홍보 랜딩페이지나 후원 결제 중심 사이트가 아니다. 시설 정보, 소식, 참여 절차, 공개 자료, 연락과 방문 안내를 방문자가 쉽게 확인하게 하는 것이 주요 역할이다.

## 주요 사용자

- 시설과 운영 정보를 확인하는 일반 방문자와 지역사회 관계자
- 거주인의 보호자와 가족
- 자원봉사 또는 후원을 검토하는 방문자
- 공개 콘텐츠를 관리하는 시설 관리자

## 제품 품질 우선순위

1. 신뢰할 수 있는 공식 정보
2. 방문자 과업 완료
3. 접근성
4. 실제 콘텐츠
5. 브랜드 표현
6. 모션과 장식

## 초기 범위

- 시설 소개, 생활 및 프로그램 안내
- 공지와 활동 소식의 목록·상세
- 후원 및 자원봉사 안내
- 운영 자료공개
- 연락 및 방문 안내
- 향후 관리자용 작성·검수·승인 기반

일반 사용자 계정, 공개 커뮤니티, 온라인 결제, 내부 행정·사례관리·의료 기록 시스템은 초기 범위가 아니다. 현재 공개 라우트와 구현은 목표 구조의 완성을 뜻하지 않는다.

## 비기능 요구사항

- WCAG 2.2 AA를 설계 목표로 삼되 전문 검증 전 적합을 선언하지 않는다.
- 모바일, 태블릿, 데스크톱에서 같은 정보와 과업을 제공한다.
- 공개에 필요한 최소 정보만 처리하고 개인정보·민감정보를 콘텐츠와 파일에 저장하지 않는다.
- 관리자 인증, 권한, 입력·파일 검증과 비밀정보 보호는 구현 시 검토한다.
- 공식 담당자가 확인한 최신 콘텐츠만 운영 공개한다.

## 개인정보 및 민감정보

거주인의 장애·진단·의료·복약·상담·개별 지원 기록, 보호자 연락처와 가족관계, 주민등록번호, 직원 인사자료, 비공개 후원자 정보, 내부 행정문서는 홈페이지 DB에서 제외한다. 정보 조합으로 개인을 식별할 가능성도 검토하며 공개 여부가 불분명하면 게시하지 않는다.

## 개발 단계용 fixture

공식 자료 확보 전에는 레이아웃과 콘텐츠 밀도, 반응형, 목록·상세·필터·빈 상태, 사진 비율과 크롭을 검증하기 위해 fixture를 사용할 수 있다. fixture는 공식 정보나 운영 공개용 콘텐츠가 아니다. 상태와 운영 분리 기준은 `content-governance.md`를 따른다.

### 허용

- `테스트 공지사항 01`, `샘플 활동소식`
- `2026년 테스트 운영자료`, `자원봉사 참여 절차 예시`
- 시설 외관·실내·활동을 표현하는 비인물 placeholder 이미지
- 테스트 데이터임을 명확히 식별할 수 있는 날짜·분류·설명

### 금지

- 실제 사람처럼 보이는 거주인 이름과 사연, 장애·건강·가족관계 정보
- 후원 계좌나 실제 모집 중인 것처럼 보이는 일정
- 실제 성과처럼 보이는 통계와 검증되지 않은 연혁
- 공식 담당자 이름
- 실제 문서로 오해할 수 있는 재무·운영자료

## 확인 필요

공식 소개 문구와 연혁, 실제 활동·프로그램, 주소·연락처, 방문 안내, 후원·자원봉사 절차, 공개 가능한 운영자료, 승인 사진, CMS·DB·인증·배포·보유기간과 승인 책임자는 운영자 확인 전 확정하지 않는다.

사랑의열매 등 타 기관은 정보구조 참고 대상으로만 검토하며 문구, 이미지, 디자인 또는 코드를 복제하지 않는다.

## 프로그램 콘텐츠 관리

프로그램은 독립 콘텐츠로 작성·검토·승인·게시하며 공개 목록과 상세에서 확인할 수 있어야 한다. 공개 정보는 분류, 제목, 요약, 목적, 본문, 선택 운영 상태 문구와 정렬 순서로 제한하고 이미지 기능은 후속 범위로 둔다.

## 활동사진 비공개 관리 1차

관리자는 JPEG·PNG·WebP 원본을 브라우저에서 WebP로 변환해 private bucket `shalom-gallery-private`에 업로드할 수 있다. binary는 Supabase Storage, 메타데이터·인물 식별 가능성·홈페이지 공개 동의·게시 기간·작성 및 승인 상태와 감사 기록은 MongoDB에 저장한다. 서버는 MIME·magic bytes·크기·SHA-256을 검증하고 MongoDB 저장 실패 시 Storage object를 보상 삭제한다. service role은 서버 전용이며 public bucket과 공개 기능은 이 단계에 포함하지 않는다.

운영 환경은 실제 값을 문서에 기록하지 않고 서버 전용
`SHALOM_SUPABASE_URL`, `SHALOM_SUPABASE_SECRET_KEY`,
`SHALOM_SUPABASE_GALLERY_PRIVATE_BUCKET`을 설정한다.

## 활동사진 검토·공개

활동사진은 초안, 검토 요청, 승인 또는 반려, 게시, 게시 중단 순서로 운영한다. 식별 가능한 인물은 확인일과 참조 코드가 있는 공개 동의 확인 상태여야 하며, 동의 철회 시 게시를 즉시 중단하고 현재 단계에서는 복구하지 않는다. 공개 기간은 Asia/Seoul의 날짜를 기준으로 판정한다.

## 자료공개 PDF 비공개 초안 관리

자료공개 PDF binary는 Supabase private Storage의 `shalom-documents-private` bucket에 최대 3MB로 한 번만 저장하고, MongoDB에는 메타데이터·상태·감사 이벤트만 저장한다. 서버는 `application/pdf` MIME, `%PDF-` magic bytes와 SHA-256을 검사한다. 문서는 초안 → 검토 요청 → 승인 또는 반려 → 게시 순서로 관리하며 개인정보 검토 완료(`confirmed`), 최종본(`final`), 미보관·미삭제가 검토 요청과 게시의 필수 조건이다. 공개 `/transparency`는 게시된 자료만 표시하고 공개 PDF API는 매 요청마다 공개 조건을 재검증해 private Storage 단일 원본을 `Cache-Control: no-store`로 전달한다. 게시 중단은 Storage 원본을 유지하면서 목록과 PDF API에서 즉시 제외해 404로 응답한다. public URL과 signed URL은 사용하지 않으며 공개 화면에는 Storage·감사·검토 내부 정보를 노출하지 않는다.

### 관리자 역할별 콘텐츠 권한

- `admin`: 전체 관리자 권한
- `editor`: 초안 작성·수정·보관·검토 요청
- `reviewer`: 승인·반려 및 활동사진 동의 철회
- `publisher`: 게시·게시 중단 및 활동사진 동의 철회
- 모든 쓰기 권한은 API에서 서버가 강제하며, UI의 작업 버튼 숨김은 보조 수단으로만 사용한다.
- 기존 `admin` 계정의 권한과 로그인 호환성은 유지한다.

## 관리자 소프트 삭제와 복구

뉴스, 프로그램, 활동사진, 자료공개 삭제는 MongoDB 문서의 `deletedAt`을 기록하는 소프트 삭제이며 영구 삭제는 지원하지 않는다. 게시 중 콘텐츠도 삭제 즉시 공개 상태가 해제된다. 활동사진 이미지와 자료공개 PDF의 Supabase Storage object는 삭제하지 않고 복구 시 그대로 재사용한다. 복구는 이전 게시 상태를 되살리지 않고 항상 `draft`·`pending` 상태로 전환하며, 검토·승인·게시 절차를 다시 거쳐야 한다. 삭제와 복구는 시스템 관리자만 수행하며 `expectedUpdatedAt` 기반 optimistic locking을 적용하고 상태 변경과 감사 이벤트를 같은 MongoDB transaction에 기록한다.

## 시스템 관리자 일반 콘텐츠 바로 게시

- 시스템 관리자는 공지사항·활동소식·프로그램 초안을 확인 checkbox로 재확인한 뒤 바로 게시할 수 있다.
- 바로 게시는 승인과 게시를 하나의 MongoDB transaction에서 처리하고 감사 기록을 남기며, UI 노출과 별도로 API가 `content.direct_publish` 권한을 강제한다.
- `editor`·`reviewer`·`publisher`의 검토 요청·승인/반려·게시 역할 분리 절차는 그대로 유지한다.
- 공개 동의가 필요한 활동사진과 개인정보·최종본 확인이 필요한 자료공개 PDF는 바로 게시 대상이 아니다.
- 내부 `news` 도메인과 경로는 유지하고 관리자 표시명만 `소식 관리`를 사용한다.

## 공식 콘텐츠 CMS 1차

시설개요와 원장 인사말은 MongoDB에서 관리하며 시스템 관리자만 수정할 수 있다. 문서가 없으면 기존 코드 기본 콘텐츠를 유지하지만 DB 장애는 기본 콘텐츠로 위장하지 않는다. 저장은 즉시 공개 페이지에 반영되고 optimistic locking을 적용하며 콘텐츠와 감사 이벤트를 같은 transaction에 기록한다. 공개 페이지의 편집 링크는 권한 있는 관리자에게만 보인다. 원장 이름은 명시적으로 공개를 설정한 경우에만 표시한다. 주민·입소자 개별 정보는 CMS 대상이 아니며 직원·생활공간 관리는 후속 단계다.

## 공식 콘텐츠 CMS 2차

직원 소개는 MongoDB에서 초안·공개·보관 상태와 표시 순서를 관리하며 시스템 관리자만 편집한다. 이름은 본인의 명시적인 홈페이지 공개 확인과 내부 확인 근거가 있을 때만 공개하고 확인 근거는 내부 전용이다. 저장은 optimistic locking을 적용하고 직원 문서와 감사 이벤트를 같은 transaction에 기록한다. 공개 페이지에는 관리자 편집 링크를 제공한다. 직원 사진과 생활공간 CMS는 후속 단계이며 입소자 개별 프로필은 구현하지 않는다.
