# 페이지 패턴

목표 라우트는 `/`, `/about`, `/life`, `/news`, `/support`, `/transparency`와 정보구조에 정의된 하위 경로다. 현재 구현은 완성 기준이 아니며 각 유형은 아래의 같은 순서로 검토한다. fixture의 상태·승인은 [`content-governance.md`](./content-governance.md), 표현은 [`design-system.md`](./design-system.md), 접근성 검증은 [`accessibility.md`](./accessibility.md)가 소유한다.

## 대표 화면 검수

홈은 기관 식별과 주요 업무 접근, 소식 목록은 검색 후 상세 확인, 찾아오시는 길은 주소 확인 후 지도 또는 문의 경로 선택을 대표 과업으로 삼는다. 기준 화면은 실제 렌더링을 확인한 뒤 정하며 이 문서만으로 시각 검수 완료를 선언하지 않는다.

| 항목      | 합격 방향                                                                           | 다시 수정할 상태                                                     |
| --------- | ----------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| 첫 화면   | 홈에서 기관 유형·업무 경로, 목록에서 검색·결과 시작, 방문 안내에서 주소·연락이 보임 | 중복 라벨·큰 제목·설명만으로 첫 화면을 소모함                        |
| 정보 밀도 | 실제 항목 수에 맞는 높이와 명확한 그룹                                              | 1건을 여러 건처럼 보이도록 늘이거나 옆 열 높이에 맞춰 빈 공간을 만듦 |
| 시각 위계 | 기관명·페이지 제목·섹션·목록 제목의 크기와 강조가 구분됨                            | 모든 제목과 링크가 같은 굵기·색·밑줄로 경쟁함                        |
| 콘텐츠    | 실제 제목·날짜·주소·절차가 중심이고 미확정 상태를 구분함                            | 승인 절차 설명이나 일반 감성 문구가 실제 정보를 대신함               |
| 상호작용  | 메뉴 현재 위치, 검색 조건·초기화, 상세 이동·복귀와 지도 경로가 예측 가능함          | 강조 메뉴를 현재 위치로 오해하거나 조건을 잃고 돌아옴                |
| 반응형    | 긴 제목·주소와 메뉴가 읽히며 정보 순서가 유지됨                                     | 잘림·겹침·페이지 전체 가로 스크롤이 발생함                           |

390px와 1440px에서 구현 전후의 첫 화면과 전체 흐름을 비교한다. 확대·키보드와 나머지 너비의 범위는 `accessibility.md`를 따른다. 0건·1건·여러 건·긴 제목·사진 유무·조회 실패를 구분해 확인하고 실행하지 않은 상태는 미검증으로 남긴다. 숫자 점수만으로 합격시키지 않는다.

## 로컬 이미지·PDF 검수 실행

공식 자료 없이 시각 검수가 필요하면 `src/content/fixtures/visual.fixture.ts`의 예시를 사용한다. 도형 WebP 3개와 한글 PDF 2쪽은 `src/content/fixtures/assets/`에 있고, `scripts/fixtures/generate-visual-assets.py`로 다시 만들 수 있다. 생성 스크립트는 Pillow·ReportLab과 Windows 맑은 고딕을 사용한다. 프로젝트 의존성을 추가하지 않고 사용 가능한 로컬 런타임에서 실행한다. 홈의 `home-still-life.png`는 별도로 생성한 인물 없는 정물 이미지이며 실제 기관 사진이 아니라는 캡션과 함께 로컬 예시 모드에서만 제공한다.

PowerShell에서 다음 설정으로 개발 서버를 실행한다. 기존 서버가 같은 포트를 사용 중이면 해당 서버를 먼저 종료한다.

```powershell
$env:SHALOM_CONTENT_SOURCE='fixture'
$env:SHALOM_VISUAL_FIXTURES='1'
pnpm dev --hostname 127.0.0.1 --port 3100
```

- `/`: 예시 사진이 있는 대표 영역을 확인한다. `SHALOM_CONTENT_SOURCE='empty'`, `SHALOM_VISUAL_FIXTURES='0'`으로 다시 실행하면 사진 없는 주요 시설 안내와 소식 0건 구성을 비교할 수 있다.
- `/life/gallery`: 원본 비율이 다른 이미지 3개와 긴 제목을 목록에서 비교한다.
- `/life/gallery/fixture-portrait`: 원본 전체 비율, 사진 설명의 줄바꿈과 원본 열기를 확인한다.
- `/life/programs/fixture-program-media`: 대표 이미지·긴 본문·긴 파일명과 PDF 내려받기를 확인한다.
- `/life/programs/fixture-program-text`: 사진·PDF·운영 상태가 없는 상세와 비교한다.
- `/transparency`: 분류·기간을 함께 선택해 결과 수, 0건, 조건 초기화와 실제 PDF 열기를 확인한다.
- `/about/greeting`, `/about/people`, `/about/spaces`: 긴 본문·역할명·공간명과 이름을 표시하거나 생략한 구성을 확인한다. 인물 사진이나 실제 직원 이름은 사용하지 않는다.

시설소개 상태를 바꾸려면 서버 실행 전에 `SHALOM_ABOUT_FIXTURE_STATE`를 `empty` 또는 `error`로 설정한다. `empty`는 직원·공간 목록 0건과 기본 인사말 안내, `error`는 세 페이지의 조회 실패를 재현한다. 정상 예시는 이 환경 변수를 해제하고 서버를 다시 시작한다. 이 설정은 위 로컬 예시 모드에서만 적용되고 오류 시뮬레이션은 실제 DB 장애나 관리자 권한 검증을 대신하지 않는다.

실행 전 예시 모드 표시를 확인한다. 같은 PDF가 여러 테스트 행에 연결되며 실제 기관 자료를 뜻하지 않는다. 390px·1440px에서 시각 검수하고 좁은 화면의 긴 파일명도 확인한다. 예시 파일 제공은 실제 Storage 업로드·승인·동의 철회 검증을 대체하지 않는다. 모드를 끄면 파일 경로가 404인지 확인한다. 운영 노출 조건은 `content-governance.md`를 따른다.

## 홈: 기관 포털형 (`/`)

### 1. 페이지 목적

공식 홈페이지의 입구로서 기관 정체성, 주요 업무, 최근 정보와 연락 경로를 한 화면 흐름에서 제공한다.

### 2. 주요 사용자 과업

기관 유형과 사이트 목적을 이해하고, 자주 찾는 업무·최근 소식·생활 정보·공개 자료·연락 경로로 이동한다.

### 3. 필수 정보와 접근 경로

| 모듈                | 필수 필드                                | 권장 노출 | 링크 목적                 | 이미지        | fixture            |
| ------------------- | ---------------------------------------- | --------- | ------------------------- | ------------- | ------------------ |
| 기관 소개 인트로    | 기관명, 시설 유형, 공식 소개, 대표 CTA   | 1개       | 시설소개 또는 최우선 과업 | 대표 1개 권장 | 허용               |
| 자주 찾는 업무      | 이름, 짧은 설명, 경로                    | 4개 안팎  | 주요 상위·하위 경로       | 불필요        | 허용               |
| 공지사항            | 제목, 분류, 게시일, 중요 여부, 상세 경로 | 4~5개     | 공지 상세·전체 목록       | 불필요        | 허용               |
| 최근 활동소식       | 제목, 날짜, 요약, 상세 경로              | 3개       | 활동소식 상세·전체 목록   | 항목별 선택   | 허용               |
| 주요 생활·지원 영역 | 이름, 설명, 경로                         | 3~4개     | 생활·지원 상세            | 선택          | 허용               |
| 생활 이야기         | 활동명, 날짜, 짧은 설명, 경로            | 3개 안팎  | 생활 기록 상세·목록       | 권장          | 허용               |
| 자료공개            | 문서명, 기준 기간, 형식, 경로            | 3개       | 문서 상세·다운로드·목록   | 불필요        | 허용               |
| 위치와 연락         | 주소·전화의 승인 상태, 방문 안내, 경로   | 1개       | 찾아오시는 길·전화        | 지도는 선택   | 테스트 정보만 허용 |

표의 개수는 충분한 데이터가 있을 때의 편집 기준이며 운영 콘텐츠의 최소 건수가 아니다. 각 행을 독립 섹션으로 만들지 않는다. 최근 공지·활동소식은 하나의 목록으로, 생활·지원 영역은 업무 탐색으로, 참여·자료공개는 보조 열로 묶을 수 있다. 홈의 연락처는 연락처 관리 데이터에서 조회한다.

### 4. 선택 모듈

승인된 긴급하지 않은 핵심 안내나 대표 문의 패널 하나를 추가할 수 있다. 실제 정보보다 감성 문구를 늘리는 모듈은 추가하지 않는다.

### 5. fixture 데이터 요구사항

0건, 1건, 여러 건과 긴 제목을 포함하고 사진이 있는 상태와 없는 상태를 구분한다. fixture 검증은 식별 가능한 개발 환경에서 수행하며 운영 정보나 실제 활동으로 사용하지 않는다.

### 6. 데스크톱 구조

첫 영역은 남색 기관 소개와 사진을 나란히 배치한다. 사진은 게시된 활동사진이며 제목과 해당 기록의 링크를 함께 보여 준다. 시설 대표 사진으로 의미를 바꾸지 않는다. 사진이 없으면 같은 자리에 직원·공간·방문 안내를 제공하고 빈 이미지 상자를 만들지 않는다. 그 아래 주요 안내 4개, 최신 소식과 참여 안내, 활동사진, 방문·문의 순으로 구성한다. 최신 소식 한 건은 제목과 요약을 크게, 나머지는 날짜와 분류를 비교하는 행으로 제공한다. 참여·자료공개는 별도 색면으로 구획하고 주소·전화는 방문 영역에 모은다.

### 7. 모바일 구조

기관 소개, 사진 또는 주요 시설 안내, 2열 업무 탐색, 소식, 참여 안내 순으로 쌓고 DOM 순서를 따른다. 대표 제목은 44px에서 시작하며 소개 버튼은 두 칸으로 정렬한다. 사진 없는 시설 안내는 보조 설명을 생략한 짧은 행으로 제공해 첫 영역이 불필요하게 길어지지 않게 한다. 사진은 원본의 핵심 맥락을 유지하고 캡션을 읽을 수 있게 한다.

### 8. 빈 상태

공지 0건은 짧은 상태 안내, 1건은 한 행, 여러 건은 정해진 수의 목록으로 표시한다. 사진 0건은 사진 영역을 생략하되 활동사진 경로를 유지한다. 문서는 짧은 자료공개 경로로 묶을 수 있다. 조회 실패는 0건과 다른 문구로 설명하며 새로고침이나 원래 목록으로 다시 접근할 수 있게 한다.

### 9. 금지 패턴

화면 절반 이상을 차지하는 감성 히어로, 오른쪽 어두운 인용문 패널, 동일 링크 타일·카드·여백의 반복, 실제 정보 없는 추상 문장과 모든 섹션의 동일한 표현을 금지한다. `HomeHero`의 현재 구현은 보존 근거가 아니다.

### 10. 완료 기준

- 첫 화면에서 기관 유형과 사이트 목적을 이해할 수 있다.
- 대표 CTA의 우선순위가 하나로 명확하고 다음 핵심 업무 일부가 첫 화면 아래에 보인다.
- 감성 문구보다 실제 정보 비중이 높고 모든 섹션이 같은 카드와 여백을 반복하지 않는다.
- 필수 모듈, 링크, fixture 변형과 빈 상태를 목표 viewport에서 검증한다.

## 시설소개: 기관 개요형 (`/about` 및 하위 경로)

하위 유형은 인사말의 승인 상태와 작성 주체를 보여 주는 **공식 메시지형**, 승인된 직원 이름·직책·업무·사진만 다루는 **승인된 직원 역할형**, 확인된 설명과 사진을 제공하는 **공간 안내형**으로 구분한다.

### 1. 페이지 목적

승인된 기관 개요와 운영 목적, 기본정보와 공간 정보를 신뢰할 수 있게 설명한다.

### 2. 주요 사용자 과업

기관의 역할과 기본정보를 확인하고 인사말·연혁·공간·찾아오시는 길로 이동한다.

### 3. 필수 모듈

소형 페이지 헤더, 공식 소개, 운영 목적, 시설 기본정보, 공간 또는 환경, 연혁·인사말·찾아오시는 길 연결을 제공한다.

### 4. 선택 모듈

승인 사진, 관련 공개자료와 대표 문의 경로를 추가할 수 있다.

### 5. fixture 데이터 요구사항

레이아웃을 검증하는 명확한 테스트 문구와 이미지 유무 상태만 제공한다. 실제 연혁·정원·인력·법인 정보는 생성하지 않고 `확인 필요`로 구분한다.

### 6. 데스크톱 구조

소형 헤더 뒤에 읽기 폭의 소개 본문과 구조화된 기본정보를 배치하고 관련 하위 페이지 링크는 보조 열 또는 후속 영역에 둔다.

시설개요의 기본정보는 페이지 본문 상단의 옅은 정보 띠로 묶는다. 넓은 화면에서는 3열, 좁은 화면에서는 레이블·값의 행으로 비교하고 값은 18~20px로 강조한다. 그 아래 생활 기준은 제목·설명의 행으로, 생활의 모습은 3열의 짧은 설명으로 구분한다. CMS의 소개·생활 기준·생활 설명은 유지하되 번호와 대형 제목을 반복하지 않는다. 공개 원칙처럼 부가적인 설명은 본문 뒤의 펼침 영역에서 읽을 수 있게 하며 관련 안내와 방문 연락처는 보조 열로 묶는다. CMS 저장 내용은 화면 개편만으로 덮어쓰지 않는다.

인사말은 소형 헤더 아래에서 상태·메시지 제목·본문·작성 주체·게시 안내 순으로 읽는다. 넓은 화면에서는 상태와 메시지 제목을 청록색 상단선이 있는 왼쪽 소개 영역, 본문과 서명을 오른쪽 읽기 영역에 배치하고 좁은 화면에서는 그 순서대로 쌓는다. 본문 폭은 `max-w-content`, 문단은 17px·줄간격 32px를 출발점으로 하고 입력한 줄바꿈을 유지한다. CMS의 문구·게시 안내와 서명 공개 여부를 보존하며 이름 공개가 꺼져 있으면 이름을 출력하지 않는다.

직원 소개는 두 자리 행 번호와 역할을 먼저, 공개된 이름은 보조 정보로 두고 담당 업무를 같은 행에 정렬한다. 게시 항목 수를 전체 직원 수처럼 표시하지 않는다. 생활공간도 두 자리 행 번호, 공간명과 설명을 같은 구조로 정렬하고 현재 데이터에 없는 공간 사진이나 출입 정보를 만들지 않는다. 두 유형 모두 작은 화면에서는 번호 옆 제목 다음에 설명이 오는 단일 열로 바뀐다.

### 7. 모바일 구조

시설개요에서는 페이지 소개, 기본정보, 생활 기준, 생활의 모습, 관련 안내와 방문 문의 순으로 단일 열을 사용한다. 기본정보는 레이블과 값 관계를 유지하고 생활의 모습도 좁은 화면에서는 세로로 읽는다.

### 8. 빈 상태

공개 직원·공간 목록이 0건이면 짧은 상태 안내와 문의 또는 방문 경로를 제공한다. 조회 실패는 0건이나 소개 준비 중으로 표현하지 않고 다시 불러오기 링크를 제공한다. 미승인 항목을 추측해 채우지 않으며 내부 승인 절차 설명을 헤더·본문에 반복하지 않는다.

### 9. 금지 패턴

거대한 `PageHero`, 검증되지 않은 숫자·연혁·조직 정보와 소개 문장마다 별도 카드를 사용하지 않는다.

### 10. 완료 기준

공식 정보와 fixture가 구분되고 기관 개요를 읽은 뒤 원하는 하위 정보와 방문 경로를 찾을 수 있다.

## 생활이야기: 사진·기록형 (`/life` 및 하위 경로)

프로그램은 카테고리·목적·설명·운영 상태를 비교하는 **분류·목록형**, 활동사진은 사진별 동의와 게시 승인을 전제로 하는 **승인 이미지 갤러리형**을 사용한다.

### 1. 페이지 목적

승인된 이미지와 구체적인 활동 기록으로 생활·활동 영역을 전달한다.

### 2. 주요 사용자 과업

카테고리를 탐색하고 최근 기록의 날짜, 활동 내용과 상세 정보를 확인한다.

### 3. 필수 모듈

카테고리, 주요 활동 영역, 최근 생활 기록을 제공한다. 각 기록의 필수 필드는 날짜, 활동명, 짧은 설명과 상세 경로다.

### 4. 선택 모듈

연도·카테고리 필터와 승인된 관련 프로그램 링크를 둘 수 있다. 공개 승인 이미지와 fixture placeholder 이미지는 선택 필드이며 이미지가 없는 기록도 정상적인 콘텐츠 상태다. 이미지 실패 시에도 날짜, 활동명, 설명과 상세 링크를 유지한다.

### 5. fixture 데이터 요구사항

짧고 긴 제목, 날짜·카테고리, 이미지 비율과 이미지 유무를 목록 카드에서 검증한다. 실제 거주인 이름, 장애·건강·가족관계와 개인 사연은 포함하지 않는다.

### 6. 데스크톱 구조

카테고리와 주요 영역 뒤에 기록 그리드 또는 목록을 두되 이미지 비율과 텍스트 밀도를 일관되게 비교할 수 있게 한다.

생활이야기 입구는 게시된 활동사진·활동소식과 프로그램 목록을 조회한다. 사진은 최대 4개, 활동소식과 프로그램은 각각 최대 3개를 출발점으로 삼고 전체 목록 경로를 제공한다. 이 개수는 최소 콘텐츠 요건이 아니다. 사진이 여러 개면 첫 기록의 사진·제목·설명을 크게 제공하고 나머지는 작은 사진과 날짜·제목의 행으로 배치한다. 사진이 한 개면 넓은 화면에서 사진과 설명을 나란히 두며, 0개면 사진 영역을 생략한다. 사진 영역 뒤에 활동소식과 프로그램 안내를 나란히 배치하고 조회 실패는 0건과 구분한다. 실제 기록 대신 하드코딩한 하루 일정이나 일반적인 생활 사례를 추가하지 않는다.

프로그램 목록은 분류·제목·요약·목적·운영 상태 순으로 읽는 행으로 구성한다. 넓은 화면에서 선택 사진은 오른쪽 보조 열, 좁은 화면에서는 설명 뒤에 둔다. 사진 없는 항목에는 빈 이미지 자리를 만들지 않는다. 제목은 20~24px, 요약은 17px, 목적·운영 상태는 15px로 구분한다. 운영 상태는 게시 데이터가 있을 때만 표시하고 조회 실패를 안내 준비 중으로 표현하지 않는다. 사진은 기존 공개 미디어 경로를 유지하며 별도 최적화 캐시를 만들지 않는다.

활동사진 목록은 데스크톱 첫 행에 해당하는 최대 3개 이미지를 즉시 불러오고 첫 이미지에만 높은 요청 우선순위를 준다. 이후 이미지는 지연 로딩한다. 모바일에서도 즉시 요청하는 수는 최대 3개로 제한한다. 상세의 단일 사진은 즉시 높은 우선순위로 요청한다. 원본 너비·높이와 목록의 `4:3` 영역, 상세의 원본 비율을 유지해 로딩 전후 배치를 안정화한다. 공개 조건을 다시 확인하는 미디어 경로와 `no-store` 정책을 유지하며 이미지 최적화 캐시나 별도 preload 요청을 추가하지 않는다.

### 7. 모바일 구조

생활이야기는 대표 기록, 나머지 짧은 사진 기록, 활동소식, 프로그램 안내 순으로 읽는다. 대표 기록의 사진은 전체 폭, 나머지는 작은 사진 옆에 날짜·제목을 두어 큰 이미지가 계속 반복되지 않게 한다. 사진 목록과 상세에서는 기록 이미지, 날짜·카테고리, 제목·설명의 관계를 유지하며 가로 카드 나열을 강제하지 않는다.

### 8. 빈 상태

선택한 카테고리에 기록이 없음을 알리고 필터 초기화나 전체 기록 경로를 제공한다. 이미지 실패 상태는 텍스트 정보와 링크를 유지한다.

### 9. 금지 패턴

일반 감성 문구로 기록을 대신하거나 미동의 인물, 개인을 추정할 정보, 사진만 있는 갤러리를 사용하지 않는다.

### 10. 완료 기준

카테고리·날짜·활동명·설명·이미지와 상세 링크의 관계가 모든 화면에서 명확하고 개인정보 없는 fixture 변형과 빈 상태를 검증한다.

## 소식 목록: 검색·분류·목록형 (`/news`)

### 1. 페이지 목적

공지와 활동소식을 검색·분류하고 중요도와 최신성을 판단해 상세로 이동하게 한다.

### 2. 주요 사용자 과업

분류·검색 조건을 적용하고 결과 수를 확인하며 중요 공지와 일반 항목을 구분해 상세를 연다.

### 3. 필수 모듈

소형 페이지 헤더, 공지·활동 분류, 검색, 적용 조건, 결과 수, 목록, 페이지 이동, 검색 결과 없음과 전체 게시물 없음 상태를 제공한다. 항목 필드는 제목, 분류, 게시일과 상세 경로다. 요약은 제목과 다른 유용한 내용이 있을 때만 표시한다. 공지에서 썸네일은 필수가 아니며 활동소식의 사진과 텍스트를 별도로 정렬할 수 있다.

### 4. 선택 모듈

기간 필터, 정렬, 첨부파일 유무와 관련 공지를 추가할 수 있다.

### 5. fixture 데이터 요구사항

중요 공지, 일반 공지, 활동소식, 긴 제목, 긴 요약, 결과 없음과 검색 결과를 포함한다. 여러 페이지를 가정할 만큼 충분한 항목을 제공하되 모두 테스트 데이터로 식별한다.

### 6. 데스크톱 구조

경로, 제목과 짧은 설명, 지역 메뉴 다음에 검색·분류 도구와 결과 수를 둔다. 제목 앞에 같은 이름의 라벨을 반복하지 않는다. 일반 목록에서 적용하지 않은 조건을 `검색어 없음`으로 늘어놓지 않는다. 검색·분류 도구 뒤에 목록이 바로 이어지며 중요 공지는 실제 상태 데이터가 있을 때만 구분한다. 검색은 옅은 중립 표면으로 묶고, 목록은 분류·제목과 요약·날짜의 세 열로 정렬한다. 제목은 18~20px, 분류·날짜·요약은 15px로 위계를 구분하며 활동사진은 제목 오른쪽의 작은 보조 이미지로 배치한다.

### 7. 모바일 구조

검색, 분류, 적용 조건·결과 수, 중요 공지, 일반 목록 순으로 배치한다. 메타데이터를 제목과 분리하되 읽기 순서는 유지한다.

### 8. 빈 상태

검색어·적용 조건과 결과가 없음을 텍스트로 알리고 조건 초기화 또는 전체 목록 이동을 제공한다. 조건 초기화와 목록 복귀 시 주소, 검색 입력값·선택값, 결과 요약이 일치해야 한다. 게시물 자체가 없을 때는 준비 중 상태를 별도로 쓴다.

### 9. 금지 패턴

거대한 히어로와 활동 카드형 갤러리를 공지 목록의 기본 구조로 쓰지 않는다. 현재 `PageHero` 호출이나 추천 카드가 목표 구조의 근거가 아니다.

### 10. 완료 기준

검색·분류·결과 수·중요 여부와 페이지 이동을 키보드와 목표 viewport에서 사용할 수 있고 긴 콘텐츠와 두 종류의 빈 상태를 검증한다.

## 소식 상세: 문서·기록 상세형 (`/news/[slug]`)

### 1. 페이지 목적

선택한 공지 또는 활동소식의 게시 정보와 본문을 중복 없이 읽게 한다.

### 2. 주요 사용자 과업

분류, 제목, 요약과 게시·수정일을 확인하고 본문을 읽은 뒤 소식 목록으로 돌아간다.

### 3. 필수 모듈

breadcrumb 또는 목록 복귀 경로, 분류, 제목, 요약, 게시일, 수정일, 개발용 fixture 여부, 본문, 첨부파일 영역 또는 첨부파일 없음 상태와 소식 목록 복귀를 제공한다.

### 4. 선택 모듈

관련 소식은 실제 데이터가 있을 때만 제공한다. 검색창, 분류 필터, 결과 수와 페이지네이션은 상세의 필수 모듈이 아니다.

### 5. fixture 데이터 요구사항

게시일과 수정일이 같거나 다른 상태, 여러 문단과 긴 제목을 검증하며 모두 개발용 예시로 식별한다.

### 6. 데스크톱 구조

소형 상세 헤더 뒤에 최대 읽기 폭의 본문을 두고 게시 정보를 별도 패널에서 반복하지 않는다.

소식·프로그램·활동사진 상세는 `ContentDetailHeader`로 목록 복귀, 분류, 제목과 날짜를 정렬한다. 공통 헤더는 청록색 상단선으로 시작하고 분류는 청록색, 메타데이터는 가는 세로선과 레이블·값의 두 단계로 구분한다. 제목은 모바일 24px, 넓은 화면 32px를 출발점으로 삼고 긴 제목을 생략하지 않는다. 상세 외곽은 `max-w-5xl`, 텍스트 본문은 `max-w-content`로 제한한다. 요약이 제목과 같으면 반복하지 않으며 갤러리 설명은 사진 아래에서 한 번만 제공한다.

소식 목록에서 상세로 이동할 때 검색어·분류·페이지와 목록 종류를 전달한다. 상세의 위·아래 목록 링크는 해당 조건을 복원하며 복귀 경로는 `/news`, `/news/notices`, `/news/activities`만 허용한다. 직접 상세 주소로 들어왔거나 잘못된 복귀 값이 있으면 `/news`로 연결한다. 검색 조건을 전달하더라도 canonical·공유 메타데이터에는 게시물 고유 주소를 유지한다.

소식과 프로그램의 `ContentAttachment`는 파일명·형식·읽기 쉬운 크기와 테두리형 내려받기 동작을 한 행에 보여 준다. 좁은 화면에서는 파일 정보 뒤에 내려받기 동작을 둔다. 파일이 없으면 짧은 한 줄 상태를 사용한다. 관련 소식 조회 실패가 이미 조회한 본문을 가리지 않게 한다. 활동사진 상세는 원본 비율을 유지하고 기존 공개 미디어 경로로 원본 보기를 제공한다.

### 7. 모바일 구조

목록 복귀, 분류·상태, 제목, 요약, 날짜, 본문과 첨부 상태 순으로 단일 열을 사용한다.

### 8. 빈 상태

첨부파일 타입이나 파일이 없으면 첨부파일 없음 상태를 제공하고 가짜 다운로드를 만들지 않는다.

### 9. 금지 패턴

목록용 검색·필터를 반복하거나 대형 히어로, 중복 게시 정보 aside와 일반 홍보 CTA를 사용하지 않는다.

### 10. 완료 기준

본문을 안전한 텍스트 문단으로 읽을 수 있고 fixture, 수정일, 첨부 상태와 목록 복귀 경로를 명확히 확인할 수 있다.

## 함께하기: 절차 안내형 (`/support` 및 하위 경로)

후원과 자원봉사는 확인 순서와 문의 경로를 우선하는 **절차 안내형**, 문의는 온라인 접수와 대표 전화·주소·방문 경로·공식 소셜 경로를 제공하는 **연락 과업형**으로 구성한다.

### 1. 페이지 목적

자원봉사와 후원의 승인된 참여 조건과 절차, 문의 방법을 혼동 없이 안내한다.

### 2. 주요 사용자 과업

참여 가능 상태와 준비사항을 확인하고 적절한 문의 경로를 선택한다.

### 3. 필수 모듈

함께하기 입구에서 후원·자원봉사 안내와 각각의 문의 접수를 구분하고 후원금 영수증·내역 문의를 별도 경로로 제공한다. 각 상세 페이지는 확인된 참여 조건·절차와 문의 방법을 우선한다. 대상·준비사항·FAQ는 실제 안내 자료가 있을 때 추가하며 미확정 항목으로 빈 패널을 만들지 않는다.

### 4. 선택 모듈

승인된 신청 경로, 세액공제·활동 전 안내와 관련 공개자료를 둘 수 있다.

### 5. fixture 데이터 요구사항

단계 수와 FAQ 길이, 참여 가능·준비 중·문의 필요 상태를 테스트한다. 미확정 계좌와 모집 일정은 fixture로도 실제처럼 쓰지 않는다.

### 6. 데스크톱 구조

두 참여 유형을 명확한 탭이 아닌 독립 섹션·경로로 구분하고 절차 단계와 문의 패널의 관계를 보여 준다.

함께하기 입구는 후원과 자원봉사를 같은 크기의 두 선택 영역으로 먼저 제시한다. 각 영역은 두 자리 순번, 유형명, 설명, 안내 보기와 문의 접수를 순서대로 보여 주며 안내 보기를 주 행동으로 둔다. 그 아래에는 영수증·내역과 일반·방문 문의를 행 목록으로 정리하고, 대표 전화와 찾아오시는 길은 청록색 상단선이 있는 하나의 문의 패널에 묶는다. 의미가 다른 참여 경로와 목적별 문의를 한 목록에 섞지 않는다.

후원·자원봉사 상세는 확인 안내 뒤에 두 자리 순번이 있는 세로 절차 행을 주 열로, 온라인 문의와 전화를 청록색 상단선이 있는 보조 패널로 제공한다. 문의 접수 링크는 기존 문의 종류 값을 전달하여 해당 종류가 선택된 입력 화면으로 연결한다. 실제 참여 확정 여부와 문의 접수를 혼동시키지 않는다. 자원봉사의 일반 문의 안내에 개발용 fixture 절차를 공식 절차처럼 연결하지 않는다.

문의 페이지는 입력 폼을 주 열, 전화·주소·외부 채널을 청록색 상단선이 있는 보조 패널로 둔다. 넓은 화면에서는 문의 종류와 이름, 전화와 이메일을 각각 두 열로 정렬하고 문의 내용과 개인정보 안내는 전체 폭을 사용한다. 입력 폼을 둥근 카드로 감싸지 않고 진한 상단선으로 시작해 다른 절차 화면과 같은 문서형 위계를 유지한다. 모바일에서도 온라인 접수 뒤에 전화 대안을 찾을 수 있어야 한다. 기존 입력 검증·동의·접수 처리 기능은 유지하고 문의 종류를 지정한 새 경로에서는 선택값을 확인한다.

### 7. 모바일 구조

유형 선택은 후원, 자원봉사 순으로 쌓고 각 영역 안에서 안내 보기와 문의 접수를 함께 제공한다. 상세에서는 대상·상태, 세로 절차, 준비사항, FAQ, 문의 순으로 단일 열을 사용하며 단계가 가로로만 이어지지 않게 한다. 데스크톱 보조 패널을 본문 뒤에 그대로 배치하므로 같은 문의 링크를 절차 앞에 반복하지 않는다.

### 8. 빈 상태

참여가 미확정이거나 중단된 경우 그 상태와 승인된 문의 방법을 제공하고 임의 절차를 대신 표시하지 않는다.

### 9. 금지 패턴

자원봉사와 후원을 한 섹션에 혼합하거나 미확정 계좌·일정·혜택을 단정하고 감정적 후원 CTA를 우선하지 않는다.

### 10. 완료 기준

사용자가 두 유형을 구분하고 대상·상태·절차·준비사항·문의까지 이해하며 미확정 항목도 명확히 식별한다.

## 자료공개: 문서 라이브러리형 (`/transparency`)

### 1. 페이지 목적

승인된 운영 자료를 기간과 유형으로 찾고 접근 가능한 방식으로 열거나 다운로드하게 한다.

### 2. 주요 사용자 과업

필터를 적용하고 문서 메타데이터와 이용 가능 상태를 확인해 상세·다운로드 또는 대체 형식을 선택한다.

### 3. 필수 모듈

문서 유형·기간 필터, 결과 수, 문서 목록과 빈 상태를 제공한다. 필수 필드는 문서명, 문서 유형, 기준 기간, 문서일, 게시일, 파일 형식, 파일 크기, 다운로드 또는 상세 경로와 자료 이용 문의 안내다. 수정일과 대체 형식은 실제 데이터가 있을 때만 표시하며 제공 여부를 추측하지 않는다.

### 4. 선택 모듈

연도 필터, 정렬, HTML 요약과 대체 형식 문의 패널을 추가할 수 있다.

### 5. fixture 데이터 요구사항

자료명에 `테스트`, `샘플` 또는 `레이아웃 검증용`임을 명시해 실제 재무자료로 오해되지 않게 한다. 필터 결과, 결과 없음, 파일 없음과 다운로드 불가 상태를 포함한다.

### 6. 데스크톱 구조

필터와 결과 수 뒤에 비교 가능한 행 목록을 두고 기간·문서일·게시일·형식·크기와 행동을 정렬한다. 분류 설명과 게시 원칙을 목록 앞의 대형 섹션으로 반복하지 않는다. 기간 선택지는 공개된 자료의 기준 기간에서 만들고 필터는 GET 주소로 유지한다. 조회 실패, 전체 0건과 필터 결과 0건을 구분하고 조건 초기화·다시 불러오기·문의 경로를 제공한다.

필터는 청록색 상단선과 옅은 중립 표면으로 한 번만 묶는다. 문서 행은 분류, 제목·요약과 세 개의 날짜 정보, 파일 형식·크기와 열기 행동의 세 영역으로 정렬한다. 제목은 19~20px, 메타데이터는 15px로 구분하고 파일 행동은 넓은 화면에서 오른쪽 경계선 뒤에 배치한다. 자료 이용 문의는 목록 아래의 짧은 청록색 안내 띠로 제공한다.

### 7. 모바일 구조

필터의 두 선택 항목은 한 행에 두되 제출 버튼은 전체 폭으로 둔다. 문서별로 분류, 제목·요약, 기준 기간·문서일·게시일, 파일 형식·크기와 열기 행동을 순서대로 쌓고 파일 영역 위에 구분선을 두어 다음 항목과 혼동되지 않게 한다.

### 8. 빈 상태

결과 없음에는 적용 조건과 초기화를, 파일 없음·다운로드 불가에는 이유와 상세 또는 대체 형식 문의 경로를 제공한다.

### 9. 금지 패턴

테스트 자료를 실제 결산·후원 자료처럼 표현하거나 파일명만 있는 타일, 불가 상태를 숨긴 비활성 버튼을 사용하지 않는다.

### 10. 완료 기준

문서의 기간·문서일·게시일·형식·크기·이용 상태를 파일을 열기 전에 알 수 있고 필터·파일 상태를 검증한다. 조건 초기화 후 선택값과 결과가 모두 전체 자료로 돌아오는지 확인한다. 실행하지 않은 파일 열기, 실제 PDF 접근성이나 장애 상태 검증은 별도로 남긴다.

## 찾아오시는 길: 지도·방문 정보형 (`/about/directions`)

### 1. 페이지 목적

승인된 위치·연락·접근 정보를 제공하고 방문 전에 확인할 사항을 알린다.

### 2. 주요 사용자 과업

주소와 외부 지도 경로를 확인하고 전화, 교통, 주차, 출입구 접근성과 방문 전 연락 필요 여부를 판단한다.

### 3. 필수 모듈

승인된 주소, 외부 지도 경로, 대표 전화와 방문 전 연락 안내를 우선 제공한다. 대중교통·주차·출입구 접근성은 확인된 자료가 있으면 추가한다. 미확정 세부 정보를 가짜 지도나 빈 표로 확장하지 않고 방문 문의로 연결한다.

### 4. 선택 모듈

승인된 건물 외관·출입구 이미지, 이동 단계와 인근 기준점을 추가할 수 있다.

### 5. fixture 데이터 요구사항

주소·전화·지도는 테스트 상태를 명시한다. 공식 확인 전 실제 교통편, 주차 가능 여부와 방문 시간을 fixture로도 단정하지 않고 미확정 표시를 검증한다.

### 6. 데스크톱 구조

작은 페이지 헤더와 지역 메뉴 뒤에 주소·외부 지도 링크를 7열, 전화·방문 문의를 5열로 배치한다. 주소 영역은 청록색 상단선과 옅은 중립 표면으로 구분하고 주소는 24~~30px, 대표 전화는 30~~36px로 읽기 쉽게 강조한다. 지도 링크는 같은 크기의 두 버튼, 문의 경로는 대표 전화 버튼과 온라인 문의 링크로 구분한다. 별도의 지도 없이도 주소 확인과 문의가 가능해야 한다. 주소·전화·방문 설명은 같은 연락처 관리 데이터에서 읽는다.

### 7. 모바일 구조

주소와 외부 지도 링크, 대표 전화와 방문 전 연락 순으로 단일 열을 사용하며 지도만 먼저 크게 노출하지 않는다. 확인된 교통·주차·접근성 자료가 있으면 그 뒤에 이어 붙인다.

### 8. 빈 상태

미승인 항목은 `확인 필요`로 표시하고 승인된 대표 문의 경로가 있을 때만 대안으로 제공한다. placeholder 지도는 실제 위치로 오해되지 않게 표시한다.

### 9. 금지 패턴

미확정 주소·교통·주차·시간을 단정하거나 placeholder 지도에 실제 위치 표현을 사용하지 않는다.

### 10. 완료 기준

사용자가 승인 정보와 미확정 정보를 구분하고 지도 없이도 주소·전화·방문 전 확인 과업을 수행할 수 있다.
